                       Signet Protocol, Version 0


Abstract

   Signet is a messaging protocol for people and their software agents.
   It is meant to replace email for parties that both support it, and to
   work alongside email for everyone else. Each address belongs to an
   identity key. The identity key signs an append-only account log that
   lists the address's clients: devices, agents, tools and an optional
   organisation escrow client. Each domain publishes its addresses
   through a directory, and every directory change is recorded in a
   Merkle-tree transparency log indexed by a verifiable random function.
   Strangers reach an address through a small, typed, end-to-end
   encrypted request. Admitted correspondents talk in threads that are
   Messaging Layer Security (MLS) groups. Messages carry signed,
   machine-readable intents with per-counterparty grants and spending
   limits for agents. Deliveries can travel through Oblivious HTTP,
   first-contact requests can be anonymous under Privacy Pass, and a
   sender can ask that a message be kept from the recipient's agents.
   Plain email continues to work in both directions, with an attested
   header that tells a Signet-aware recipient the sender can be reached
   on Signet.

   This document specifies version 0 of the protocol (wire label
   signet0), as implemented by the reference code.

   This document is an Internet-Draft-style specification. It is not an

   no formal standing.

   It describes version 0 of Signet. The reference implementation is the
   library (@signet/lib), native core (@signet/mls), server
   (@signet/server) and client (@signet/client). Where the reference

1.  Introduction

   Email addresses are the most widely shared identifiers on the
   Internet, but email itself has three problems that get worse as
   software agents start to read and write mail for people. First, the
   sender of a message is a claim, not a fact: SPF, DKIM and DMARC
   [RFC7208] [RFC6376] [RFC7489] authenticate domains, not people, and
   are applied inconsistently. Second, anyone can send anything to
   anyone, so the cost of unwanted mail falls on the recipient. Third, a
   message is prose. An agent has to guess what a message asks for, and
   the recipient has no way to tell what an agent acting for the sender
   is allowed to agree to.

   Signet keeps the address and changes what stands behind it. An
   address resolves to an identity key and a set of certified clients.
   Unknown senders can send only a small, typed request. Conversations
   happen in end-to-end encrypted groups. Messages can carry structured
   intents, and an agent's authority to make them is stated in signed
   grants that only the counterparty sees.

1.1.  Goals

   Signet version 0 aims to:

   1.  Keep existing addresses. A Signet address is an ordinary
       local@domain address [RFC5322]. A domain can adopt Signet without
       changing its MX records or its existing mail provider.

   2.  Make sender identity verifiable end to end. Every Signet request
       and message is signed by a client key that the sender's identity
       key certified, that the sender's domain bound, and that a public
       transparency log recorded.

   3.  Make key substitution detectable. A domain cannot show different
       keys for one address to different people, or silently rebind an
       address, without a public record that the address's owner
       monitors.

   4.  Put the recipient in control of first contact. Unknown senders
       are limited to one small request with one typed intent. The
       recipient's own clients, not its server, decide who is admitted.

   5.  Treat agents as first-class, bounded clients. Agents have their

       own keys and certificates. What they may do is set by private
       scopes and limits, and by per-counterparty grants that the
       counterparty can verify.

   6.  Encrypt content end to end. Servers store and forward only
       ciphertext. Threads use MLS [RFC9420].

   7.  Reduce the metadata servers learn, using sealed-sender delivery,
       Oblivious HTTP [RFC9458] and Privacy Pass [RFC9576].

   8.  Stay interoperable with email in both directions.

1.2.  Non-goals

   Signet version 0 does not aim to:

   *  Move money. The pay.request and pay.sent intents carry a request
      for payment and a statement that payment was made. Payment itself
      happens outside Signet.

   *  Stop lookalike domains. Signet prevents sending _as_ a domain. It
      cannot prevent someone from registering a similar domain. Clients
      warn about lookalikes (Section 7.6).

   *  Prevent a recipient from showing a message to anyone, including
      its own agents. The humans-only audience (Section 11) is a request
      the recipient's policy honours, not a technical control over the
      recipient.

   *  Hide all metadata. Servers still see thread-epoch linkage, timing
      and sizes (Section 15).

   *  Replace the transport, storage or user interface of any mail
      system.

   *  Define a federated transparency log with gossip between operators.
      Version 0 trusts one log per domain policy (Section 5.8).

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",

1.4.  Conventions

   *  All binary values in JSON are base64url without padding (Section 5
      of [RFC4648]), written "b64u" below.

   *  Public keys are raw keys in b64u: 32 bytes for Ed25519 [RFC8032]
      and X25519 [RFC7748].


Foss                    Expires 15 May 2027                     [Page 6]

   *  A hash written as a string has the form sha256: followed by the
      b64u SHA-256 digest of the input.

   *  Timestamps are strings in the format produced by ECMAScript
      Date.prototype.toISOString, for example 2026-11-11T09:30:00.000Z.
      This is a profile of [RFC3339] in UTC with millisecond precision.

   *  "Canonical JSON" means the serialization defined in Section 3.2.
      Every signature in this document is an Ed25519 signature over the
      UTF-8 bytes of the canonical JSON of the signed object, unless
      stated otherwise.

   *  Identifiers created by Signet are a short prefix, an underscore
      and 12 random bytes in b64u, for example c_3qX0… for a client, g_…
      for a grant, r_… for a request, m_… for a message and t_… for a
      thread.

   *  HTTP routes are relative to the home server's base URL as given in
      the domain policy (Section 6.2).

   *  Example addresses use example.com and example.net.

                      Figure 1: Signet components

   Private keys stay on clients, and each client talks only to its own
   home server. Servers do the rest: they bind addresses to identity
   keys, record every change in the transparency log, get blinded tokens
   from the issuer, relay sealed deliveries through OHTTP, and exchange
   plain email. Every server does what Alice's does; the lower arrows
   are drawn from one side only to keep the picture readable.

2.1.  Accounts and Clients

   A Signet account is an address, such as alice@example.com, and an
   identity key. The identity key signs an account log. The log lists
   the account's clients. Each client has its own Ed25519 signing key
   and X25519 agreement key, a kind (device, agent, tool or org-escrow),
   private scopes and limits, and an expiry. The identity key signs only
   the log, two derived documents (the public card and the contact view)
   and grants. Day-to-day work is done with client keys.

   The identity key can be rotated, and it can be replaced once through
   a recovery key if it is lost (Section 3.6).

2.2.  Domains, Directory and Log

   A domain announces Signet support with a _signet TXT record and
   serves a JSON policy over HTTPS. The policy names the domain key, a
   VRF public key, the transparency log the domain writes to, and
   optionally an Oblivious HTTP gateway and a Privacy Pass issuer.

   The home server stores each account's log, card and contact view. It
   cannot create or change them, because they are signed by the identity
   key. It binds each address to its identity key with a signature by
   the domain key. Every change is appended to the transparency log as a
   leaf at the address's VRF index. Clients pin identity keys on first
   use, follow the key chain on the card when a key changes, and treat
   any other change as an identity change.

2.3.  Three Tiers of Visibility

   *  The public card, for anyone: the identity key, unlabeled request
      keys, keys for humans-only mail, the intake agent if any, and the
      key chain.

   *  The contact view, for people the owner has admitted: each active
      client's keys and whether it is a device, an agent or the escrow
      client.

   *  The account log, for the owner and its home server only: labels,
      scopes and limits.

   An agent's authority toward one counterparty is a grant signed by the
   identity key and shown only to that counterparty.

2.4.  First Contact and Conversations

   A sender who is not yet admitted sends a request: one signed object
   of at most 8192 bytes, with a subject, at most one typed intent, a
   short note, an optional introduction, and the sender's own contact
   view. It is sealed with HPKE separately to each request key on the
   recipient's card. The recipient's clients decide admission locally,
   using contacts, the own domain, trusted domains, introductions and a
   lookalike-domain check.

   Accepting a request starts a thread. A thread is an MLS group whose
   leaves are the current reading clients of every participant. Messages
   inside it are signed JSON bodies carried as MLS application messages.
   Clients join a group, and apply a commit, only after checking every
   member against its owner's contact view as recorded in the
   transparency log.

2.5.  Metadata Protection

   A client talks only to its own home server. The home server makes
   lookups, key-package claims and log queries on the client's behalf,
   signed as its domain, and names the requester only by a hash. Thread
   traffic carries no sender: the recipient's server accepts it on a

2.7.  Message Path

   The following path shows a first contact from alice@example.com to
   bob@example.net, Bob's acceptance, and one thread message. It assumes
   both domains publish policies and Bob's domain accepts Privacy Pass.

   1.   Alice's client resolves example.net: it reads
        _signet.example.net TXT and fetches the policy from the host it
        names (Section 6).

   2.   Alice's client asks its home server GET
        /v0/lookup?address=bob@example.net. Alice's server fetches GET
        /v0/directory/bob?requester=<hash> from Bob's server, signed
        with the example.com domain key.

   3.   Bob's server returns Bob's domain binding, signed card and VRF
        proof. It returns the contact view only if Bob released it to
        Alice.

   4.   Alice's client verifies the binding, the card, the VRF proof and
        the key chain, then asks its home server for the latest log leaf
        at Bob's VRF index (GET /v0/transparency/latest). It checks the
        inclusion proof, the signed tree head and consistency with the
        last tree head it saw. It pins Bob's identity key (Section 5.6).

   5.   Alice's client registers the hash of a fresh reply token with
        its home server (POST /v0/delivery-tokens) and releases its
        contact view to Bob (POST /v0/contacts/grant).

   6.   Alice's client gets a Privacy Pass token: it blinds a token
        request for origin example.net and sends it to its home server
        (POST /v0/tokens). The home server rate-limits Alice and
        forwards it to the issuer, signed as example.com. Alice's client
        unblinds the signature.

   7.   Alice's client builds the request, signs it with its client key,
        checks the 8192-byte limit, and seals one copy to each request
        key on Bob's card with HPKE.

   8.   Alice's client submits it (POST /v0/submit) with the Privacy
        Pass token and no sender. Alice's server encapsulates POST

Foss                    Expires 15 May 2027                    [Page 13]

Experimental           Signet Protocol, Version 0          November 2026

        /v0/deliver-anonymous with Bob's OHTTP key and sends it through
        the relay. The relay forwards it to Bob's gateway.

   9.   Bob's server checks the token (valid, unspent, bound to
        example.net) and stores the request in Bob's mailbox with an
        empty sender.

   10.  Bob's client fetches its mailbox (GET /v0/mailbox), opens its
        copy, looks up Alice (steps 2 to 4 in reverse), checks Alice's
        presented contact view against the log, checks the signature and
        any intent authority, and runs admission (Section 7.5).

   11.  Bob accepts. Bob's client claims key packages for every reading
        client of Alice and Bob through its home server (POST
        /v0/claim), creates an MLS group, registers the thread's
        delivery-token hash, and submits the welcome. The welcome to
        Alice is sealed with Alice's reply token, so it carries no
        sender.

   12.  Alice's server accepts the welcome because the reply token
        hashes to a value Alice registered. Alice's clients check every
        member in the welcome against its owner's contact view, join,
        and register the new delivery-token hash.

   13.  Alice's client sends a message: it signs a message body,
        encrypts it as an MLS application message, and submits it with
        the thread's current delivery token. Each recipient server
        accepts it on the token and stores it with no sender.

   14.  Bob's clients decrypt it, check that the MLS sender is a current
        client in Alice's contact view, check the message signature and
        the authority for each intent, and show it.

3.  Identities, Clients and the Account Log

3.1.  Overview

   Each Signet address has one identity key at a time. The identity key
   signs a hash-linked account log. Replaying the log from its first
   entry gives the account's current state: its identity key, its
   clients, its intake agent, its audience policy, its revoked grants,
   its key chain and its recovery key.

   The identity key MUST be used to sign only these objects:

   *  account log entries (Section 3.5);

   *  key links of type rotate and set-recovery (Section 3.6);

   *  the public card and the contact view (Sections 4.3 and 4.4);

   *  grants (Section 9.6).



Foss                    Expires 15 May 2027                    [Page 14]

Experimental           Signet Protocol, Version 0          November 2026

   The recovery key MUST be used to sign only recover key links, the log
   entries that carry them, and recovery proofs (Section 3.9).

3.2.  Canonical JSON and Signatures

   Every signature in Signet is computed over the canonical JSON
   serialization of an object, encoded as UTF-8. Implementations MUST
   serialize signed objects with the JSON Canonicalization Scheme (JCS)
   [RFC8785]. Signed objects MUST be I-JSON [RFC7493]: no duplicate
   member names, no lone surrogates, and numbers that are IEEE 754
   double-precision values.

   An Ed25519 signature [RFC8032] over an object o with key k is:

      sig = b64u(Ed25519-Sign(k, UTF-8(JCS(o))))

   Unless a section says otherwise, the signed object is the object with
   its sig member removed. A verifier removes sig, serializes what
   remains, and verifies. Some objects add a fixed type member before
   signing that is not present on the wire; each such case is stated
   where it applies.

   A hash of an object, written H(o), is sha256: followed by the b64u
   SHA-256 digest of UTF-8(JCS(o)).

   A conforming implementation MUST reject non-I-JSON input when signing
   or verifying rather than serialize it.

3.3.  Identity Key

   The identity key is an Ed25519 key pair. Its public key is published
   in the genesis entry of the account log, in the domain binding
   (Section 4.2), on the public card and in the contact view.

   The private identity key SHOULD be held on as few devices as
   possible, and SHOULD be held in hardware-backed storage where
   available. Clients other than the one that holds the identity key
   MUST NOT need it for normal operation.

   An implementation SHOULD keep the identity key in hardware-backed
   storage and SHOULD NOT export it. A new client MUST generate its own
   signing and agreement keys and send only the public halves to the
   holder of the identity key for certification.

3.4.3.  Active Clients

   A client is active at time t when all of the following hold:

   1.  its certificate is in the log;

   2.  no revoke-client entry names it;

   3.  notBefore <= t < expires.

   Only active clients appear on the card and in the contact view, may
   authenticate to the home server, and may be offered as MLS members.

   The client chooses clientId, so it knows its id before it is
   approved. The identity holder MUST:

   1.  Check that type is enroll, that principal is its own address,
       that ts is within 15 minutes of now, and that sig verifies with
       sigKey.

   2.  Show the person the kind, label, requested scopes and limits, and
       the request's fingerprint.

   3.  Choose the certificate's scopes, limits and expiry itself. The
       request's values are only a request.

   4.  Append an add-client entry whose certificate carries the
       request's clientId, sigKey and agreeKey, and publish (Section
       3.10).

   The fingerprint is computed over the SHA-256 digest of the canonical
   JSON of body: each of its first 16 bytes, reduced modulo 32, picks a
   character of the Crockford base32 alphabet, written in four groups of
   four (for example 7K2M-QX9D-A4HT-0RWE). Both devices display it.

   *Link or QR code.* The request travels as signet:enroll?r= followed
   by the b64u of its canonical JSON. The channel is authenticated by
   presence (a QR code on the new device's screen) or by its source (a
   link from the service being connected); comparing fingerprints covers
   a channel that is not. After approval the new client authenticates
   with its own key (Section 3.11) and reads its certificate from its
   own log (Section 4.9).

   *Pairing code.* For a client that is somewhere else. A code has the
   form DDDD-XXXX-XXXX: the four digits name a relay slot on the home
   server, and the eight Crockford base32 characters are a secret the
   server never sees.

   1.  A device of the account opens a slot with POST /v0/pairing

Experimental           Signet Protocol, Version 0          November 2026

       (client-authenticated; device clients only). The server returns
       the slot and an expiry 10 minutes later, and the device shows the
       code.

   2.  Both sides run SPAKE2 over the Ed25519 group with the secret as
       the password. The owner is side A, with identity signet pair v0
       <principal> <slot> owner; the new client is side B, with identity
       signet pair v0 <principal> <slot> new client. Each posts its
       message (POST /v0/pairing/{slot}/a with client authentication,
       POST /v0/pairing/{slot}/b without) and reads the other's (GET
       /v0/pairing/{slot}/{side}?after=n).

   3.  Each side derives two AES-256-GCM keys from the SPAKE2 output
       with HKDF-SHA256, an empty salt and the info strings signet pair
       v0 request and signet pair v0 reply. The AAD is signet pair v0.

   4.  The new client posts its enrollment request sealed under the
       request key. If the owner cannot open it, the codes differed: the
       owner posts any unreadable message, so the new client fails at
       once, and stops.

   5.  The owner checks and decides as above, then posts {"cert":
       <ClientCert>} or {"refused": "<reason>"} sealed under the reply
       key. The new client MUST check that the certificate carries its
       own clientId, sigKey, agreeKey and principal.

   The server MUST accept at most two messages per side in a slot, so a
   wrong guess uses the slot up. It MUST limit the slots an account
   opens and the unauthenticated posts a source makes per day, and MUST
   delete slots once they expire. Because the server sees only SPAKE2
   messages and ciphertext, it can neither learn the code nor substitute
   keys, and an attacker gets one guess at a 40-bit secret per slot.

      signed by the same recovery key. After it, no recovery key is set:
      a recovery key can be used once.

   A key link applies to a state (principal, identityKey, recoveryKey)
   as follows. Any failed check is an error, and the whole log or chain
   is rejected.

   1.  If link.principal is not the state's principal, or link.from is
       not the state's identity key, fail ("changes a key that isn't
       current").

   2.  If rotate: verify sig with the current identity key; set the
       identity key to to.

   3.  If set-recovery: verify sig with the current identity key; set
       the recovery key to recoveryKey.

   4.  If recover: require a recovery key to be set, link.recoveryKey to
       equal it, and sig to verify with it; set the identity key to to;
       clear the recovery key.

   The ordered list of all signed key links in the log is the account's
   key chain. The public card carries it (Section 4.3).

   +---------+    rotate      +---------+     recover       +---------+
   |  key 1  |--------------->|  key 2  |------------------>|  key 3  |
   +---------+  signed by     +----+----+  signed by R      +---------+
                key 1              |                          only key 3
                                   | set-recovery R           now signs
                                   | signed by key 2          valid
                                   v                          grants
                            +--------------+
                            | recovery     |
                            | key R        |  kept offline;
                            +--------------+  used once, then cleared

          Figure 2: Key chain with a rotation, then a recovery

   A contact who pinned key 1 follows both links and is told the key was
   recovered. Grants signed by key 1 or key 2 stop counting; only key 3
   signs valid grants (Section 3.8).

3.7.  Replaying the Log

   A verifier replays a log to check it and to compute its state. The
   state has: principal, identity key, head, clients (by id), revoked

Foss                    Expires 15 May 2027                    [Page 24]

Experimental           Signet Protocol, Version 0          November 2026

   client ids, intake, revoked grant ids, agents that read humans-only
   mail, key chain and recovery key.

   1.  If the log is empty or entry 0 is not genesis, fail.

   2.  Set principal and identity key from entry 0's body. Set every
       other part of the state to empty, the intake to null and the
       recovery key to null. Set prev to null.

   3.  For each entry at position i:

       1.  If entry.seq != i or entry.prev != prev, fail ("out of
           order").

       2.  If the body is a key-change whose link type is recover, the
           signer is the current recovery key. Otherwise the signer is
           the current identity key.

       3.  If there is no signer, or entry.sig does not verify with the
           signer over {seq, prev, ts, body}, fail.

       4.  Apply the body: genesis fails unless i == 0; key-change
           applies the key link (Section 3.6) and appends it to the key
           chain; add-client fails if cert.principal is not the
           principal, if cert.clientId was used before (even by a
           revoked client), or if cert.kind is org-escrow and the scopes
           do not cover read:*, and otherwise adds it; revoke-client
           fails if the client id is unknown, adds it to the revoked
           set, and clears the intake if it was the intake; set-intake,
           if not null, fails unless the named client exists, has kind
           agent and is not revoked, then sets the intake; revoke-grant
           adds the grant id to the revoked set; set-audience-policy
           fails if any id is not a known client, then replaces the set;
           set-listing sets whether the principal is unlisted (Section
           4.11).

       5.  Set prev to the entry hash of this entry.

   4.  Set the head to prev.

   A home server MUST replay a log before storing it. A client MUST
   replay a log it receives as the owner (Section 4.5) and MUST check
   that the replayed identity key, principal and head match the domain
   binding and the card.

3.8.  Following Key Changes

   A correspondent that pinned an identity key (Section 5.6) and later
   sees a different one MUST NOT accept it unless the card's key chain
   leads from the pinned key to the new one.

   The key history of a card is computed from card.principal,
   card.keyChain (empty if absent) and card.identityKey:


Foss                    Expires 15 May 2027                    [Page 25]

Experimental           Signet Protocol, Version 0          November 2026

   1.  Start a state with the principal, the identity key equal to
       keyChain[0].link.from (or card.identityKey if the chain is
       empty), and no recovery key. Start the key list with that key.

   2.  For each link in order, apply it (Section 3.6). If the link is
       not set-recovery, mark the last key in the list as ended by
       rotated (for rotate) or recovered (for recover), and append the
       new identity key.

   3.  If the final identity key is not card.identityKey, fail.

   A card whose key history fails MUST be rejected.

   Given a key history and a pinned key P:

   *  If P is not in the key list, the change is not explained by the
      chain. The client MUST treat it as an identity change (Section
      5.6).

   *  If any key from P up to (not including) the current key ended by
      recovered, the change is a recovery.

   *  Otherwise the change is a rotation.

   When a client accepts a change, it MUST replace the pin with the new
   key and SHOULD report a key-changed event:

      { "kind": "key-changed", "principal": "alice@example.com",
        "how": "recovered", "from": "<pinned key>",
        "to": "<current key>" }

   The reference client reports the event for other people's addresses
   whether the change was a rotation or a recovery, and for its own
   address only when it was a recovery. A client SHOULD present a
   recovery more prominently than a rotation, because a recovery means
   the old key was lost and may be in someone else's hands.

   The grant keys of a key history are the keys from the one that
   follows the last recovered mark to the current key. If there is no
   recovery, all keys are grant keys. A grant (Section 9.6) is valid
   only if signed by a grant key. Grants signed by a key in use before
   the last recovery therefore stop counting.

   When an owner monitors its own address (Section 5.7), a log leaf
   bound to any key in its own key history is not an alert.

3.9.  Recovery

   Recovery is for an owner who has lost the identity key, and possibly
   every device, but holds the recovery key.





Foss                    Expires 15 May 2027                    [Page 26]

Experimental           Signet Protocol, Version 0          November 2026

3.9.1.  Recovery Proof

   To obtain the stored log, the owner proves possession of the recovery
   key to its home server:

      POST /v0/recovery/{local}
      Content-Type: application/json

      { "ts": "2026-11-11T09:30:00.000Z", "sig": "b64u signature" }

   sig is the recovery key's signature over:

      { "type": "signet recovery", "principal": "alice@example.com",
        "ts": "2026-11-11T09:30:00.000Z" }

   The type member is not sent; the server adds it when verifying. The
   server:

   1.  finds the account for {local} (lowercased);

   2.  replays the stored log;

   3.  checks that a recovery key is set, that |now - ts| is less than 5
       minutes, and that sig verifies with the recovery key over the
       object above, with principal set to the stored log's principal.

   On success it returns 200 with {"entries": [ ...LogEntry ]}. On any
   failure, including an unknown address, it MUST return 404 with the
   same body, so that the route does not reveal which addresses exist or
   have a recovery key.

   The server MUST rate-limit this route per address and per source, and
   MUST accept each proof at most once: a replayed proof gets the same
   404, because a proof replayed within its 5-minute window would
   otherwise return the private log again.

3.9.2.  Recovery Procedure

   1.  The owner obtains the stored log (Section 3.9.1), or uses a copy
       it already holds.

   2.  The owner replays it. The principal MUST match, and the log's
       recovery key MUST equal the owner's recovery public key.

   3.  The owner generates a new identity key.

   4.  The owner appends a key-change entry with a recover link: from is
       the log's current identity key, to is the new key, recoveryKey is
       the recovery key. Both the link and the entry are signed by the
       recovery key.

   5.  The owner signs a new card and contact view with the new identity
       key and publishes them (Section 3.10.2).


Foss                    Expires 15 May 2027                    [Page 27]

Experimental           Signet Protocol, Version 0          November 2026

   After recovery:

   *  Existing client certificates remain. The owner SHOULD review them
      and revoke any it does not recognise, because whoever holds the
      old identity key may have added clients.

   *  Grants signed before the recovery stop counting (Section 3.8). The
      owner MUST reissue any it still wants.

   *  No recovery key is set. The owner SHOULD set a new one.

   A recovery key protects against loss, not theft. Whoever holds the
   identity key can replace the recovery key with set-recovery. If a
   thief rotates the key before the owner recovers, recovery still works
   as long as the thief has not also replaced the recovery key, because
   recover applies to whatever identity key is current.

3.10.  Publication

3.10.1.  Publication Object

   The owner publishes its log together with a card and view signed for
   the current head:

      {
        "entries": [ { "seq": 0, "prev": null, "ts": "…", "body": {
          "type": "genesis", "principal": "alice@example.com",
          "identityKey": "…" }, "sig": "…" } ],
        "card": { "card": { "v": 0, "type": "card", "…": "…" },
          "sig": "…" },
        "view": { "view": { "v": 0, "type": "view", "…": "…" },
          "sig": "…" }
      }

   A home server checks a publication as follows:

   1.  Replay entries (Section 3.7).

   2.  Verify the card and view with the replayed identity key (Sections
       4.3 and 4.4), including the card's key history.

   3.  Require card.logHead and view.logHead to equal the replayed head.

   Failure of step 3 is 400 "card and view must be signed for the
   current log head". A replay or signature failure is also 400.

3.10.2.  Updating a Published Log

      POST /v0/log/{local}
      Content-Type: application/json

      <Publication>



Foss                    Expires 15 May 2027                    [Page 28]

Experimental           Signet Protocol, Version 0          November 2026

   The route needs no client authentication: everything in it is signed.
   The home server:

   1.  returns 404 if {local} is not enrolled;

   2.  checks the publication (Section 3.10.1);

   3.  returns 409 "log must extend the stored log" unless the new log
       is at least as long as the stored one and every stored entry has
       the same entry hash as the entry at the same position;

   4.  returns 200 without change if the card hash and view hash are
       unchanged;

   5.  appends a bound leaf for the new identity key, card hash and view
       hash to the transparency log (Section 5.3); if the log refuses,
       returns 502 and stores nothing;

   6.  if the replayed identity key differs from the bound key, makes a
       new domain binding for the new key (Section 4.2);

   7.  stores the log, card and view.

   Step 6 is how a rotation or recovery reaches the directory. The
   domain rebinds only to a key the log itself reached through signed
   key links.

3.10.3.  Enrollment

   Enrollment creates the first binding for an address. The home server
   checks the publication (Section 3.10.1), requires the principal's
   domain to be its own (400 otherwise), appends a bound leaf, signs a
   domain binding and stores the account.

   A home server MUST authenticate enrollment through the organisation's
   own administration process, and MUST NOT replace an existing account
   through enrollment. Replacing an account is a rebinding: it MUST be a
   deliberate administrative act, and it is visible in the transparency
   log (Section 5). A home server MUST store accounts durably and MUST
   NOT lose an accepted log update.

   Unenrollment appends an unbound leaf (Section 5.3) and deletes the
   account. The reference server offers it only as an administrative
   function, not over HTTP.

3.11.  Client Requests to the Home Server

   A client authenticates every call to its own home server with four
   headers:

   +==================+================================================+
   | Header           | Value                                          |
   +==================+================================================+
   | signet-principal | The client's address.                          |
   +------------------+------------------------------------------------+
   | signet-client    | The client id.                                 |
   +------------------+------------------------------------------------+
   | signet-ts        | The current time.                              |
   +------------------+------------------------------------------------+
   | signet-sig       | The client signing key's signature over the    |
   |                  | object below.                                  |
   +------------------+------------------------------------------------+
   | signet-nonce     | 16 random bytes, b64u, fresh for every call.   |
   |                  | Covered by the signature as the nonce field of |
   |                  | the signed object.                             |
   +------------------+------------------------------------------------+

   The signed object is:

      {
        "kind": "client",
        "method": "POST",
        "path": "/v0/submit",
        "ts": "2026-11-11T09:30:00.000Z",
        "body": "sha256:47DEQpj8HBSa-_TImW-5JCeuQeRkm5NMpJWZG3hSuFU"
      }

   method is uppercased. path is the request target exactly as sent,
   including the query string. body is the hash of the raw request body
   bytes (the hash of the empty string when there is none).

   The server MUST reject the call with 401 if:

   *  a header is missing;

   *  the principal's domain is not the server's domain, or the
      principal is not enrolled;

   *  the client is not active in the principal's log (Section 3.4.3);

   *  signet-ts is more than 5 minutes from the server's clock;

   *  the signature does not verify with the client's sigKey.

   The server MUST also reject with 401 a call whose signature it has
   already accepted. Because every call carries a fresh signet-nonce
   that the signature covers, two honest calls never share a signature,
   so the server keeps the (signet-principal, signet-client, signet-sig)
   of each accepted call for at least twice the 5-minute window (it may
   arrive up to 5 minutes early or late) and refuses a repeat. It checks
   this only after the signature verifies, so nobody can fill the cache
   with junk.

   The server MUST replay the stored log for each authentication, or
   keep a replayed state that it updates when the log changes, so that a
   revoked or expired client is refused at once.

4.6.  Domain Authentication

   A home server calling another Signet service (another home server, a
   transparency log or a Privacy Pass issuer) signs the call as its
   domain:

   +===============+===================================================+
   | Header        | Value                                             |
   +===============+===================================================+
   | signet-domain | The calling domain.                               |
   +---------------+---------------------------------------------------+
   | signet-ts     | The current time.                                 |
   +---------------+---------------------------------------------------+
   | signet-sig    | The domain key's signature over the object below. |
   +---------------+---------------------------------------------------+
   | signet-nonce  | 16 random bytes, b64u, fresh for every call.      |
   |               | Covered by the signature as the nonce field of    |
   |               | the signed object.                                |
   +---------------+---------------------------------------------------+

      {
        "kind": "domain",
        "domain": "example.com",
        "method": "GET",
        "path": "/v0/directory/bob?requester=sha256%3A…",
        "ts": "2026-11-11T09:30:00.000Z",
        "body": "sha256:47DEQpj8HBSa-_TImW-5JCeuQeRkm5NMpJWZG3hSuFU"
      }

   The receiver resolves the calling domain's policy (Section 6) to get
   its domain key, and MUST reject the call with 401 if signet-ts is
   more than 5 minutes from its clock or the signature does not verify.
   If the calling domain's policy cannot be resolved, the reference
   server returns 400.

   The receiver (a home server, transparency log or Privacy Pass issuer)
   MUST also reject with 401 a call whose (signet-domain, signet-sig) it
   has already accepted, keeping each for at least twice the 5-minute
   window, and checking only after the signature verifies.

4.7.  Remote Lookup

      GET /v0/directory/{local}?requester={hash}

   Other home servers call this route with domain authentication
   (Section 4.6). requester names the user on whose behalf the lookup is
   made, as a requester hash:

      requesterHash(address) = sha256("{domain}|{local}@{domain}")

Foss                    Expires 15 May 2027                    [Page 38]

Experimental           Signet Protocol, Version 0          November 2026

   where the address is lowercased and the hash is computed over the
   UTF-8 string and written in sha256: form. Calls without signet-domain
   are anonymous.

   The server answers as follows:

   1.  If the call is domain-authenticated, refuse with 429 if the
       calling domain is scanning (step 6).

   2.  Choose counters: for an authenticated call, one per calling
       domain and one per (domain, requester); for an anonymous call,
       one per source IP address. If any counter has reached its daily
       limit (Section 4.10), refuse with 429.

   3.  If the call is authenticated and the owner released the view to
       requester (Section 4.8), the access level is contact. Otherwise
       it is public.

   4.  Build the entry (Section 4.5) at that access level. The log is
       never included.

   5.  Add 1 to each counter for an enrolled answer, or the miss weight
       (10) for a not-enrolled answer.

   6.  For an authenticated call, count the lookup and, if it missed,
       the miss, against the calling domain. A domain that has made at
       least 50 lookups today, more than half of which missed, is
       scanning, and its lookups are refused for the rest of the day.

   Rate limits apply to remote lookups but MUST NOT change the content
   of an answer. A lookup refused for rate reasons returns 429, never a
   not-enrolled entry.

4.8.  Releasing the Contact View

      POST /v0/contacts/grant
      Content-Type: application/json

      { "add": ["sha256:…"], "remove": ["sha256:…"] }

   A client (Section 3.11) adds or removes requester hashes to which its
   account's contact view is released. A client SHOULD release its view
   to each person it sends a request to, starts a thread with, or
   accepts, before doing so. The reference client does this in
   sendRequest and startThread.

4.9.  Lookups by Own Clients

      GET /v0/lookup?address={address}

   A client asks its own home server to look up any address. The server:

   1.  If the address is on its own domain: for the client's own
       address, returns the entry at owner level (with view and log);

       otherwise returns the entry at contact level if colleagues may

4.11.  Unlisted Addresses

   Unlisted addresses are OPTIONAL at two levels. A domain MAY run an
   intake. A principal on such a domain MAY choose to be unlisted.
   Neither is the default.

   *Domain intake.* A domain that runs an intake publishes its HPKE key
   in the policy (Section 6.2). keyId is computed as for a request key
   (Section 4.3). The home server holds the private key.


Foss                    Expires 15 May 2027                    [Page 40]

Experimental           Signet Protocol, Version 0          November 2026

      "intake": { "keyId": "sha256:…",
        "agreeKey": "<X25519 public key, b64u>" }

   *Opting out.* A principal becomes unlisted with a set-listing log
   entry (Section 3), and lists itself again with "unlisted": false. A
   home server whose domain has no intake MUST reject a publication
   whose log leaves the principal unlisted, with HTTP 409.

      { "type": "set-listing", "unlisted": true }

   *Answers.* When the domain runs an intake, the home server MUST
   answer a public-access directory read for an unlisted principal, and
   for any address that has no account, with an unlisted entry signed by
   the domain key:

      { "status": "unlisted", "principal": "bob@example.net",
        "ts": "2026-11-11T09:30:00.000Z",
        "sig": "<Ed25519 over the other fields>" }

   The entry MUST NOT carry a VRF proof, binding, card or any other
   field that differs between the two cases. Without a VRF proof the
   requester cannot find the address's leaf in the transparency log, so
   the log does not tell them apart either. Contact and owner access
   (Sections 4.8 and 4.9) are answered as usual: contacts the principal
   released its view to, and colleagues where the domain allows it, see
   the full entry. A server SHOULD still count real misses toward its
   scanning limits (Section 4.10); the requester cannot see which it
   was.

   *Clients.* A client that receives an unlisted entry MUST verify its
   signature with the domain key and MUST check that the policy names an
   intake. It MUST NOT treat the answer as "not enrolled", so there is
   no plain-email fallback, and MUST NOT change a pin it already holds.
   It reaches the address only through a request to the intake (Section
   7.11). Operations that need the recipient's contact view, such as
   joining a thread, wait until the principal releases its view.

   *Trade-off.* The intake can read first-contact requests to unlisted
   principals. After acceptance the principal's view is released to the
   sender (Section 4.8), the sender verifies it against the log as for
   any listed address, and the thread is end-to-end encrypted. A domain
   could also claim that a listed principal is unlisted in order to read
   its first-contact requests. A domain can already withhold those
   requests, so this adds exposure of their content but no new power
   over delivery.

   *Keeping the domain honest.* For a stranger with no other
   information, whoever holds the VRF key decides what the stranger
   sees, so a false "unlisted" cannot be ruled out. These rules make it
   detectable, and useless against anyone with prior contact:

   1.  *Cross-check.* A client that receives an unlisted entry through
       its home server MUST repeat the lookup anonymously: GET
       /v0/directory/{local}, unsigned, through an Oblivious HTTP relay

Foss                    Expires 15 May 2027                    [Page 41]

Experimental           Signet Protocol, Version 0          November 2026

       when it has one (the gateway answers these lookups with the
       public entry, on the same per-source budget as any unsigned
       lookup). If the anonymous answer is an enrolled entry, the client
       MUST verify it as usual, use it instead of the intake, and report
       the inconsistency to the person. If it is a not-enrolled answer,
       the client MUST NOT send through the intake.

   2.  *Owner check.* A principal's own clients SHOULD make the same
       anonymous lookup of their own address when monitoring (Section
       5.7), and alert if strangers are told a listed principal is
       unlisted or not enrolled, shown an unlisted principal, or shown a
       card other than the current one. The domain cannot tell this
       lookup from a sender's cross-check, so lying consistently to
       senders means lying to the owner too.

   3.  *Prior contact.* A client MUST NOT send through the intake to an
       address whose identity key it has pinned, or from which it has
       received plain email with an authenticated Signet header field
       (Section 13.5). It reports that the domain says the address is
       unlisted, and asks for a contact card.

   4.  *Contact cards.* A principal MAY hand out a contact card: its
       domain binding, signed card and VRF proof, as signet:card?e=
       followed by the b64u of their canonical JSON. A client that holds
       one verifies it as an enrolled entry, including the
       transparency-log check, and uses it whenever the domain answers
       unlisted, so it reaches the principal's own keys even when the
       principal really is unlisted. A card whose card hash no longer
       matches the log's latest leaf is out of date: the client MUST NOT
       use it, and MUST NOT fall back to the intake.

   A domain can still lie selectively to particular requesters. The
   owner's check catches it only for anonymous lookups, which is why the
   cross-check also uses that path.

4.12.  Open Issues

   *  *Requester hashes are asserted, not proven.* The requester
      parameter is chosen by the calling home server. A dishonest home
      server can spread one user's lookups over many hashes, or present
      the hash of someone the target released its view to. The
      per-domain limit and the scanning rule bound the first. The second
      would release a contact view to the wrong server. The view holds
      no labels or scopes, but it lists client keys. A future version
      should bind the requester to a proof from the requesting client.

   *  *Requester hashes are guessable.* requesterHash is an unkeyed hash
      of an address. Anyone who can guess an address can compute it. It
      hides addresses from casual inspection, not from a determined
      observer.

   *  *Domain key rotation.* Version 0 has no way to rotate a domain key
      other than publishing a new policy. Bindings signed by the old key
      stop verifying when the policy changes. A future version should

Foss                    Expires 15 May 2027                    [Page 42]

Experimental           Signet Protocol, Version 0          November 2026

      specify an overlap period.

5.  Key Transparency

5.1.  Overview

   Every change to a directory entry is appended to a transparency log:
   an append-only Merkle tree with the hashing and proofs of Section 2.1
   of [RFC9162]. Each leaf commits to an address's identity key, card
   hash and view hash at the time of the change. Leaves are filed under
   the address's VRF index, so the log does not reveal which addresses
   are enrolled.

   A home server cannot show one key to some people and another key to
   others, or quietly rebind an address, without either leaving a leaf
   the owner's own clients will see (Section 5.9) or failing the checks
   correspondents make on every lookup (Section 5.8).

5.2.  VRF Index

   Each domain holds a VRF key pair for ECVRF-EDWARDS25519-SHA512-TAI
   (suite string 0x03) as defined in Section 5 of [RFC9381]. The public
   key is published as vrfKey in the domain policy (Section 6.2), as 32
   bytes in b64u.

   For an address, the VRF input is:

      alpha = UTF-8("signet0 " || lowercase(local) || "@" ||
        lowercase(domain))

   The VRF proof pi (80 bytes) and output beta (64 bytes, from
   ECVRF_proof_to_hash) are carried as:

      { "index": "b64u(beta)", "proof": "b64u(pi)" }

   The address's index is b64u(beta).

   A verifier MUST run ECVRF_verify with the domain's vrfKey, the
   address's alpha and proof, and MUST reject the entry if verification
   fails or if the resulting beta does not equal index. Only the domain
   can compute an index. It proves it on every lookup, so nobody can
   test guessed addresses against the log offline.

   The reference implementation is in libs/signet-mls/src/vrf.rs and is
   checked against the test vectors of [RFC9381].

5.7.  Proxied Log Queries

   Clients query the log through their own home server:

      GET /v0/transparency/latest?log={url}&index={index}
      GET /v0/transparency/history?log={url}&index={index}
      GET /v0/transparency/consistency?log={url}&first={m}&second={n}

   The home server MUST refuse with 400 a log URL that is not one of the
   logs it is configured to query (by default, only its own domain's
   log), so that it cannot be used to fetch arbitrary URLs. It forwards
   the query to the log with domain authentication and the client's
   requester hash, and relays the answer. An upstream 429 is returned as
   429; any other failure as 502.

   A client whose own home server refuses it (401) MAY query the
   directory and log directly, without authentication, within their
   per-IP budgets. The reference client does this only while monitoring
   its own address (Section 5.9).

5.8.  Verifying a Lookup

   A client MUST verify every directory entry before using it. For an
   address A on domain D, with pinned key P (if any):

   1.   Resolve D's policy (Section 6).

   2.   Find a trusted log whose URL and key both equal the policy's
        log. If none, fail: the domain writes to a log this client does
        not trust.

   3.   Fetch the entry (Section 4.9).

   4.   If the entry is not-enrolled:

        1.  Verify that its principal's domain is D and its signature
            verifies with the domain key, and verify the VRF proof
            (Section 5.2), giving the index.

        2.  Fetch the latest leaf at the index and verify it (step 7).

Foss                    Expires 15 May 2027                    [Page 47]

Experimental           Signet Protocol, Version 0          November 2026

        3.  If the latest leaf is bound, fail: the log says the address
            is enrolled.

        4.  If P exists and the latest leaf is not unbound, fail with an
            identity change (presented = none). If P exists and the leaf
            is unbound, remove the pin.

        5.  Return "not enrolled".

   5.   Otherwise verify the entry:

        1.  The principal's domain is D.

        2.  binding.principal equals the entry's principal, and the
            binding signature verifies with the domain key (Section
            4.2).

        3.  The card verifies for the principal and binding.identityKey,
            including its key history (Section 4.3).

        4.  The view, if present, verifies for the same principal and
            key (Section 4.4).

        5.  The VRF proof verifies, giving the index.

        6.  The log, if present, replays (Section 3.7), and its identity
            key, principal and head equal the binding's key, the
            principal and card.logHead.

   6.   Fetch the latest leaf at the index (Section 5.7).

   7.   Verify the tree head and leaf:

        1.  The tree head signature verifies with the trusted log key.

        2.  The tree head is consistent with the last one this client
            saw from that log (Section 5.8.1).

        3.  If a leaf is returned, the proof's treeSize equals the
            head's size and the inclusion proof verifies against the
            head's root.

   8.   Require a leaf of kind bound whose identityKey equals

5.8.1.  Tree Head Consistency

   A client keeps the largest signed tree head it has seen from each
   log. On each new head h from log L, with stored head s:

   1.  If h does not verify with L's key, fail.

   2.  If s.size == h.size and s.root != h.root, fail: the log has
       forked.

   3.  If s.size < h.size, fetch a consistency proof from s.size to
       h.size and verify it. If it fails, fail: the log has forked.

   4.  If there is no s, or s.size < h.size, store h.

   A head smaller than s is accepted without a proof and not stored.

5.9.  Monitoring

   Each client SHOULD periodically check its own address's history:

   1.  Look up the client's own address. If the home server refuses the
       client (401), report "your home server no longer accepts this
       client" and repeat the lookup directly against the public
       directory (Section 5.7). If the lookup fails with an identity
       change, report that the address is bound to a key the client does
       not hold.

   2.  Compute the account's own keys: every key in the card's key
       history if the lookup succeeded, otherwise the pinned key.

   3.  Fetch the full history at the address's index. Verify the tree
       head (Section 5.8.1) and each leaf's inclusion proof.

   4.  For each leaf, report an alert if it is unbound, or if it is
       bound to a key that is not one of the account's own keys.

   5.  Report every active client in the contact view that this client
       has not seen before, with its kind and label, so the owner can
       confirm it.

5.10.  Log Trust

   A client is configured with a set of trusted logs, each a URL and an
   Ed25519 key. It MUST refuse addresses whose domain policy names any
   other log. Version 0 trusts the log for "latest leaf" answers: a log
   that withholds a newer leaf can make a client accept a stale entry,
   until the owner's monitoring sees the newer leaf.

5.11.  Open Issues

   *  *One operator.* Version 0 assumes a single log per domain and no
      gossip between clients or monitors. A deployment SHOULD run at
      least two independent log operators and have clients compare tree
      heads.

6.  Discovery

6.1.  Overview

   A domain supports Signet when it publishes a _signet TXT record and
   serves a policy document over HTTPS. Discovery does not use MX
   records, so a domain can keep its existing mail provider for plain
   email and run Signet on a separate host. The design follows MTA-STS
   [RFC8461]: a DNS record announces the policy, the policy is fetched
   over HTTPS from a host under the domain's control, and a cached
   policy resists downgrade.

6.3.  DNS Record

   A domain announces Signet with a TXT record at _signet.<domain>:

      _signet.example.net.  IN TXT  "v=signet0; host=signet.example.net"

Foss                    Expires 15 May 2027                    [Page 51]

Experimental           Signet Protocol, Version 0          November 2026

   A client parses the TXT records as follows:

   1.  Join the character-strings of each TXT record into one string.

   2.  Select the first record whose trimmed text matches v=signet0
       followed by ; or the end of the string. If none matches, the
       domain does not support Signet.

   3.  Split the record on ;. Trim each part. Each part of the form
       key=value is a field; the key and value are trimmed and
       lowercased. Parts without exactly one = are ignored.

   4.  If a host field is present, it MUST be a hostname made of
       letters, digits and hyphens in dot-separated labels, with no
       label starting or ending in a hyphen, and it MUST equal the
       domain or end with . followed by the domain. If either check
       fails, the domain does not support Signet. Otherwise the
       candidate hosts are [host].

   5.  If there is no host field, the candidate hosts are
       signet.<domain>, then <domain>.

   The host restriction keeps control of the policy with whoever runs
   the domain's zone. A host on another domain is refused.

6.4.  Fetching the Policy

   For each candidate host in order, the client fetches:

      GET https://<host>/.well-known/signet.json

   1.  The client MUST NOT follow redirects. A redirect response counts
       as a failure for that host. This stops a website that redirects
       /.well-known/ to another host from choosing the policy.

   2.  A response that is not successful, is not JSON, has v other than
       signet0, or has domain other than the domain being resolved
       counts as a failure for that host.

   3.  The first host that succeeds gives the policy.

   4.  If every host fails, the domain does not support Signet.

   A home server MUST serve its policy at GET /.well-known/signet.json.

6.5.  Caching and Downgrade Resistance

   A client SHOULD try to refresh a domain's policy on each use. When it
   fetches a policy successfully, it caches it until now + maxAge.

   If a refresh fails (no TXT record, DNS failure, HTTPS failure, or no
   valid policy) and the client holds a cached policy for the domain
   that has not expired and has mode equal to enforce, the client MUST
   use the cached policy. This stops an attacker who can block DNS or

Experimental           Signet Protocol, Version 0          November 2026

   HTTPS from making a known Signet domain look like a plain email
   domain.

   A cached policy with mode equal to testing gives no such protection:
   a failed refresh is reported as a failure. A domain SHOULD use
   testing while it sets Signet up and enforce after.

6.6.  Running Alongside Existing Mail

   Because discovery uses only _signet and the policy host, a domain can
   keep its MX, SPF, DKIM, DMARC and MTA-STS records pointed at its
   existing mail provider. A typical setup:

   +===============================+===================================+
   | Record                        | Value                             |
   +===============================+===================================+
   | MX, SPF, DKIM selectors,      | Unchanged.                        |
   | _dmarc, _mta-sts              |                                   |
   +-------------------------------+-----------------------------------+
   | _signet.example.net TXT       | v=signet0;                        |
   |                               | host=signet.example.net           |
   +-------------------------------+-----------------------------------+
   | signet.example.net            | The Signet home server, or a      |
   |                               | CNAME to a hosted one.            |
   +-------------------------------+-----------------------------------+

   In this setup the home server does not receive plain email. Clients
   send plain email through the existing provider (Section 13.6).

6.7.  Open Issues

   *  *The domain key is not pinned.* A successful refresh replaces the
      cached policy, including domainKey, vrfKey and log, with no
      continuity check. An attacker who can obtain a valid certificate
      for the policy host and answer its DNS can substitute a domain
      key. Pinned identity keys and the transparency log still catch a
      substituted identity key (Section 5.8), but the attacker can sign
      legacy-mail attestations and server-to-server calls. A future
      version should log domain policies in the transparency log or
      require continuity between domainKey values.

   *  *server is unconstrained.* The host field must be under the
      domain, but the policy's server URL may point anywhere. This
      allows hosted providers, and also means the policy host decides
      where all traffic goes.

7.1.  Overview

   A sender who has no thread with a recipient sends a request. A
   request is small (at most 8192 bytes before sealing), says who the
   sender is, carries at most one typed intent and a short note, and is
   sealed end to end to the recipient's request keys. The recipient's

   server sees the recipient, the size and, unless the request is
   anonymous, the sender. It never sees the content.

   The recipient's own clients decide whether to admit the sender. The
   home server does not make that decision.

7.3.  Sealing

   The sender looks up the recipient (Section 5.8) and selects keys: the
   card's humanKeys if the request is humans-only, otherwise the card's
   requestKeys. If the list is empty, the sender MUST NOT send, and
   reports that the recipient has no client that can receive the
   request.

   *  empty aad.

7.4.  Sending

   Before sending, the reference client:

   1.  generates a random 32-byte reply token and registers
       deliveryTokenHash(token, ownAddress) with its home server
       (Section 10.3);

   2.  releases its contact view to the recipient (Section 4.8);

   3.  builds and seals the request, including grants it holds that name
       the recipient;

   4.  submits it with kind request (Section 10.2), anonymously if the
       recipient's domain accepts Privacy Pass, unless told otherwise
       (Section 10.5);

   5.  adds the recipient to its contacts (Section 7.9).

   The recipient's home server applies two daily limits to signed
   requests from one sender to one recipient: 5 per sender address and
   100 per sender domain. Requests over either limit are listed as
   rejected in the delivery result. Anonymous requests are limited to
   200 per recipient per day.

7.5.  Opening and Verifying

   A recipient client opens a request as follows:

   1.  Find the copy whose clientId equals the keyId of this client's
       agreeKey. If there is none, ignore the request.

   2.  Open it with HPKE using info = signet0 request  followed by this
       client's own address, and parse the JSON.

   3.  If body.to is not this client's address, or the envelope has a
       from that differs from body.from, fail ("envelope does not match
       its contents").

   4.  Look up body.from (Section 5.8). An anonymous request names the
       sender only inside, so the lookup happens after decryption.

   5.  Check the presented senderView: it MUST verify for the sender's
       principal and identity key, and its view hash MUST equal the view
       hash in the sender's latest log leaf. Otherwise fail ("not
       current").

   6.  Find body.fromClient among the view's members. It MUST be present
       and not expired, and sig MUST verify with its sigKey over body.
       Otherwise fail ("not signed by an active sender client").

   7.  If there is an intent, check the sender's authority for it
       (Section 9.5), with the request's grants.

   sender's clients to a thread while that view remains current (Section

7.7.  Admission

   Each account has an admission policy:

      { "contacts": ["carol@example.org"],
        "trustedDomains": ["example.org"] }

   An address is trusted by the account me if, after normalization:

   1.  it is in contacts (reason contact); or

   2.  its domain is me's domain (reason same organisation); or

   3.  its domain is in trustedDomains (reason trusted domain <domain>).

   The recipient client decides admission for a verified request:

   1.  If the sender is trusted, admit.

   2.  If the sender's domain is a lookalike of a known domain (Section
       7.8), do not admit, and report the domain it imitates.

   3.  If there is an introduction: if the introducer is not trusted, do
       not admit; otherwise look up the introducer, and if the
       introduction is valid (Section 7.6), admit with the
       introduction's context as the reason; otherwise do not admit.

   4.  Otherwise do not admit ("unknown sender").

   Admission is evaluated only on the recipient's clients. A request
   that is not admitted waits in the recipient's request queue for a
   person (or an agent with the authority) to accept or ignore it.

   To accept a request, the reference client adds the sender to its
   contacts and starts a thread with the sender (Section 8.5), passing
   the request's replyToken and making the thread humans-only if the
   request was. Signet version 0 sends nothing when a request is
   ignored.

7.8.  Lookalike Domains

   Signet stops anyone sending as a domain. It does not stop someone
   registering a domain that reads like another. Clients warn about such
   domains.

   The known domains for an account are its own domain, its trusted
   domains and the domains of its contacts. A domain d is a lookalike of
   a known domain k if d is not itself known and either:

   *  skeleton(d) == skeleton(k); or

   *  both are at least 6 characters long and their Levenshtein distance
      is at most 1.


Foss                    Expires 15 May 2027                    [Page 60]

Experimental           Signet Protocol, Version 0          November 2026

   skeleton(x) is computed by applying Unicode NFKC normalization,
   lowercasing, replacing every i with l, and then, in order: replacing
   rn with m, vv with w, 0 with o, 1 and | with l, 5 with s, and
   removing -.

   A client MUST NOT admit a request from a lookalike domain on the
   strength of trust alone, and MUST NOT put legacy mail from a
   lookalike domain in the inbox tier (Section 13.4). The skeleton above
   is a minimal set. A client SHOULD also apply the confusables data of
   Unicode Technical Standard #39 [UTS39].

7.9.  Shared Contacts

   The reference home server stores each account's contacts and trusted
   domains, so that every client of the account admits the same people
   and warns about the same lookalikes:

      GET  /v0/contacts
      POST /v0/contacts   { "contacts": ["…"], "trustedDomains": ["…"] }

   Both require client authentication (Section 3.11). POST adds the
   given entries (lowercased) and never removes any. GET returns
   {contacts, trustedDomains}. Each client merges the stored lists into
   its own on every sync.

7.11.  Requests Through a Domain Intake

   When a lookup returns an unlisted entry (Section 4.11), the sender
   seals the request as in Section 7.3, but with the intake key from the
   recipient domain's policy in place of the card's keys: one copy whose
   clientId is the intake keyId, using the HPKE info string for the
   recipient address. Everything else is unchanged: the body, the size
   limit, the signature, any Privacy Pass token and the delivery routes.
   A humans-only request is also sealed to the intake; the server
   applies the audience in step 4.

   On receiving a request with a copy for its intake keyId, the
   recipient's home server:

Experimental           Signet Protocol, Version 0          November 2026

   1.  MUST apply the same per-sender, per-domain and anonymous limits
       as for any request (Section 4.10).

   2.  MUST open the copy with the intake key, and MUST drop the request
       if it cannot, if the plaintext exceeds 8192 bytes, if body.to
       differs from the envelope address, or if the envelope names a
       sender other than body.from.

   3.  MUST drop the request if the address has no account.

   4.  Otherwise MUST seal the unchanged plaintext again to each key on
       the principal's card: humanKeys when body.audience is "humans",
       otherwise requestKeys. It stores the result as an ordinary
       request, with a sender on the envelope only if the original had
       one.

   5.  MUST return the same delivery result in every case, so that the
       sender cannot tell a dropped request from a delivered one.

   The recipient's client opens and verifies the forwarded request
   exactly as in Section 7.5. The sender's signature inside is
   untouched, so the intake can read or drop a request but cannot alter
   it. The sender releases its own contact view before sending (Section
   7.4), so a recipient can verify an unlisted sender as well.

7.12.  Open Issues

   *  *Contacts are visible to the home server.* The shared-contacts
      routes (Section 7.9) store an account's contacts and trusted
      domains on its home server in the clear, so that all of its
      clients admit the same people. The admission decision is still
      made on the client. A future version should store the lists
      encrypted to the account's clients.

   *  *No removal.* Contacts and trusted domains can be added but not
      removed through the shared-contacts routes.

8.  Threads and Messages

8.1.  Overview

   A thread is an MLS group [RFC9420]. Its members are the reading
   clients of every participant: each person's devices and agents that
   hold read:*, and the escrow client if the organisation has one. Every
   leaf uses the client's own certified Ed25519 key, so an MLS member is
   exactly a certified Signet client.

   The MLS layer decides cryptographic membership. Signet decides who is
   allowed to be a member. A client joins a group, and applies a commit,
   only after it has checked every credential the welcome or commit
   carries against the owner's current contact view as recorded in the
   transparency log.



Foss                    Expires 15 May 2027                    [Page 63]

Experimental           Signet Protocol, Version 0          November 2026

8.2.  MLS Profile

   Signet version 0 uses MLS 1.0 [RFC9420] with:

   *  cipher suite MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519
      (0x0001);

   *  a basic credential whose identity is UTF-8(JCS({"principal": P,
      "clientId": C})) for principal P and client id C;

   *  the client's certified sigKey as the leaf signature key;

   *  the ratchet_tree extension in every Welcome, so joiners need no
      separate tree download;

   *  a wire format policy that sends every handshake and application
      message as a PrivateMessage;

   *  padding of every PrivateMessage to a multiple of 256 bytes;

   *  a group id of 16 random bytes.

   Commits carry only Add and Remove proposals, by value. Standalone
   proposals are not used and MUST be rejected. Only commits from
   current members are accepted; external commits are not used.

   The thread id is the string t_ followed by the b64u group id.

   A member that cannot parse a credential identity as the JSON object
   above, with string principal and clientId, MUST reject the welcome,
   commit or message that carries it.

8.3.  Key Packages

   Each reading client publishes MLS KeyPackages to its own home server
   so that others can add it to threads.

      GET  /v0/keypackages/count     → { "count": 3,
        "lastResort": true }
      POST /v0/keypackages           { "packages": [ { "kpId": "kp_…",
        "keyPackage": "b64u" } ],
                                       "lastResort": { "kpId": "kp_…",
                                         "keyPackage": "b64u" } }

   Both routes need client authentication (Section 3.11). One-time
   packages are added to the client's queue. lastResort, if present,
   replaces the client's last-resort package. Every KeyPackage declares
   support for the last_resort extension in its leaf capabilities; the
   last-resort package also carries that extension and MAY be handed out
   more than once, so draining a client's one-time packages cannot lock
   it out of new threads. The reference client keeps 5 one-time packages
   and one last-resort package and tops them up on every sync.

Experimental           Signet Protocol, Version 0          November 2026

   To add another person's clients, a client claims packages through its
   own home server:

      POST /v0/claim
      { "address": "bob@example.net",
        "clients": ["c_P0hn3aL2vTq1xYb0aLcd",
        "c_Xq81mZ0aL2vTq1xYb0aL"] }

      → { "packages": [ { "clientId": "c_P0hn3aL2vTq1xYb0aLcd",
        "kpId": "kp_…", "keyPackage": "b64u" } ] }

   For an address on its own domain, the home server serves the claim
   itself. Otherwise it calls the other domain's claim route with domain
   authentication and the client's requester hash:

      POST /v0/directory/{local}/claim?requester={hash}
      { "clients": [ "…" ] }

   The serving home server:

   1.  refuses with 401 a claim without domain authentication: key
       packages are handed only to Signet servers;

   2.  refuses with 429 once the calling domain exceeds its daily claim
       limit;

   3.  refuses with 404 if {local} is not enrolled;

   4.  for each requested client id that is active (Section 3.4.3),
       refuses with 429 once that (domain, requester, client) exceeds
       its daily claim limit, and otherwise removes and returns the
       client's oldest one-time package, or the last-resort package if
       none remain;

   5.  silently omits client ids that are not active or have no package.

   Before using a claimed package, the claiming client MUST check that:

   1.  the KeyPackage parses, is valid for MLS 1.0, and uses the cipher
       suite of Section 8.2;

   2.  its credential identity names the expected principal and client
       id, and claimed.clientId names the same client;

   3.  its leaf signature key equals the sigKey for that client in the
       owner's verified contact view.

8.5.  Starting a Thread

   To start a thread with a set of addresses, optionally humans-only and
   optionally linked to an existing thread, a client:

   1.  Looks up its own address. If the thread is humans-only and this
       client is not a humansOnly member of its own view, fails.

   2.  Normalizes the other addresses, removes duplicates and its own
       address.

   3.  Releases its contact view to them (Section 4.8).

   4.  For its own address and each other address, looks up the contact
       view and selects the members that are readers, not expired, and
       (for a humans-only thread) humansOnly. It excludes itself. If a
       participant's view is not available, it fails.

   5.  Claims a key package for each selected member and checks each one
       (Section 8.3).

   6.  Creates the MLS group with itself as the first member and adds
       all claimed packages in one commit.

   7.  Registers the thread's delivery-token hash (Section 10.3).

   8.  Builds a welcome payload (Section 8.6). If any joiner is on its
       own account, submits the welcome to its own address. If there are
       other participants, submits the welcome to them, sealed with the
       request's reply token if one was given (Section 10.3).

8.7.  Sending and Receiving Messages

   Thread traffic is carried in this payload:

      { "thread": "t_4l5Rz2kqQm8x0aL2vTq1xQ",
        "mls": "b64u MLSMessage(PrivateMessage)" }

   To send, a client builds and signs a message body (after checking its
   own authority for each intent, Section 9.4), encrypts the JSON as an
   MLS application message, and submits it with kind message to every

Foss                    Expires 15 May 2027                    [Page 69]

Experimental           Signet Protocol, Version 0          November 2026

   participant, sealed with the thread's current delivery token (Section
   10.3).

   A client receiving a message:

   1.  Ignores it unless it is a member of thread.

   2.  Decrypts it, obtaining the MLS sender's credential and leaf
       signature key.

   3.  Checks the sender against its owner's contact view as in Section
       8.6 step 3.

   4.  Parses the body and verifies that body.thread equals the thread;
       that body.from equals the sender's principal and body.fromClient
       the sender's client id; that sig verifies with the sender's
       sigKey; and that every intent passes the receiver-side authority
       check (Section 9.5) with the message's grants.

   5.  Reports a message event, with the sender's kind and its shared
       label, if any.

   6.  Applies the effects of session.end and handoff.human (Section
       12).

   A message that fails any check MUST NOT be shown as a message. The
   reference client reports an error event.

8.8.  Membership Changes

   A client brings a thread in line with everyone's current contact
   views with a rekey:

   1.  For each participant principal, looks up the current directory
       entry.

   2.  Marks for removal every member, other than itself, that is no
       longer a current, unexpired member of its owner's view with the
       same sigKey, or (in a humans-only thread) is no longer
       humansOnly.

   3.  For each participant whose view is available, claims packages for
       every eligible member not already in the group.

   4.  If there is nothing to remove or add, stops.

   5.  Creates one commit with the removals and additions and applies it
       locally.

   6.  Submits the commit to every participant and, if there are
       joiners, a welcome to their principals, both sealed with the
       delivery token of the epoch before the commit.

   7.  Registers the new epoch's delivery-token hash.

Foss                    Expires 15 May 2027                    [Page 70]

Experimental           Signet Protocol, Version 0          November 2026

   Revoking a client in the account log does not by itself remove it
   from threads. A rekey by any member does. Clients SHOULD rekey
   threads when they learn that a participant's view has changed.

   A client receiving a commit:

   1.  Ignores it unless it is a member of the thread.

   2.  Stages the commit without applying it, obtaining the sender, the
       added members and the removed leaves.

   3.  Unless the commit removes this client, checks the sender, and
       each added member, against their owners' views as in Section 8.6
       step 3. In a humans-only thread every added member MUST be
       humansOnly. Any failure rejects the commit, and the group state
       is left unchanged.

   4.  Applies the commit.

   5.  If this client was removed, or the group is no longer active,
       forgets the thread, deregisters all its delivery-token hashes,
       and reports removed.

   6.  Otherwise registers the new delivery-token hash and reports
       rekeyed with the new epoch, members and participants.

8.9.  Attachments

   Attachments are encrypted by the sender and uploaded as opaque blobs.
   The key travels only inside the encrypted message.

   1.  The sender generates a random 32-byte key and a random 12-byte

       additional data signet0 attachment. The 16-byte tag is appended
       to the ciphertext.

   2.  The sender uploads the ciphertext to its own home server with
       POST /v0/blobs (client-authenticated, body: raw bytes), which
       returns { "id": "blob_…", "url":
       "https://signet.example.com/v0/blobs/blob_…" }.

   3.  The sender puts an attachment reference in the message:

8.10.  Client State

   A client's MLS key store, pins, tree heads, registered token hashes,
   thread metadata and grants are its private state. The reference
   client saves them as a snapshot, so that it can stop and resume. The
   MLS core is functional: every call takes the serialized key store and
   returns a new one, so a failed call or a previewed commit leaves the
   stored state unchanged.

8.11.  Open Issues

   *  *Commit ordering.* MLS needs the delivery service to order commits
      within an epoch. Signet version 0 has no ordering service: if two
      members commit in the same epoch, members may apply different
      commits and the group forks. A conforming implementation SHOULD
      designate a committer per thread (for example the thread creator's
      home server) or adopt a resolution rule, and members MUST detect
      and recover from a fork.

   *  *Thread ids are visible to servers.* The thread field of the
      payload and the welcome is sent in the clear. Servers can link all
      traffic of a thread, not just of an epoch.

   *  *Blob URLs are bearer capabilities.* Anyone with the URL can
      download the ciphertext, and version 0 has no way to revoke one. A
      server SHOULD expire blobs and SHOULD use unguessable ids.

9.1.  Overview

   An intent is a typed action carried in a request or a message, so
   that software can act on it without guessing from prose. Who may send
   an intent is limited in two places:

   *  On the sending side, the owner's own clients enforce the sending
      client's private scopes and limits (Section 9.4).

   *  On the receiving side, the receiver cannot see scopes. It accepts
      an agent's intent only if the agent is the sender's intake for
      that intent, or presents a grant from its owner that names the
      receiver (Section 9.5).

9.2.  Intent Format

9.3.1.  Payment Intents

   Signet never moves money. Payment happens wherever the two parties
   already pay each other. pay.request carries the ask and pay.sent
   carries the receipt, each signed by the client that sent it.


Foss                    Expires 15 May 2027                    [Page 74]

Experimental           Signet Protocol, Version 0          November 2026

   *  pay.request.link, if present, is where the requester says payment
      can be made. A receiver MUST treat it as untrusted input. An agent
      MUST NOT pay through it unless its owner has separately authorised
      that payment.

   *  pay.sent is a statement by the payer, not proof of payment. A
      receiver MUST NOT treat it as settlement until it has confirmed
      the payment through the payment channel itself.

   *  reference links the two: a payer SHOULD put the requester's
      reference, or the payment system's own reference, in pay.sent.

   Both payment intents carry amountUsd, but neither commits anyone to
   anything: one asks to be paid and the other reports a payment. They
   therefore have no _committed amount_ and are exempt from the amount
   limits in Sections 9.4 and 9.5. Every other intent with a numeric
   args.amountUsd commits that amount. A sender still needs the
   intent:pay.* scope, and a receiver still requires the sending agent
   to be the intake for the intent or to hold a grant.

       draft, the verified context, the audience and its hash. It goes
       to a thread whose members are only the owner's own clients, and
       MUST NOT go anywhere else.

   things:

   *  Release to the thread. The client MUST recompute the audience hash
      and refuse to send if it differs from the card's, telling the
      person who joined; the person must approve again.

   *  Release to the requester only, in the humans-only sibling (Section
      11), so the requester's devices and any agents they opted in
      receive it, and their other agents do not.

   *  Release a narrower answer than the draft, with decision:
      "narrowed".

   *  Refuse.

   them from any agent in the thread without a grant (Section 9.5); the

9.4.  Sender-Side Authority

   A client MUST check each intent before it sends it:

   1.  Validate the intent (Sections 9.2 and 9.3).

   2.  If the client is a device, allow it.

   3.  Let name be the intent name without its version. Unless name is
       handoff.human, the client's scopes MUST cover intent:name
       (Section 3.4.2). Otherwise refuse.

   4.  If the intent has a committed amount (Section 9.3.1), it MUST NOT
       exceed the client's limits.commit_usd (0 if absent). Otherwise
       refuse with a limit error.

   A limit error means the agent has reached the edge of its authority.
   The agent SHOULD hand the thread to its owner (Section 12.6) rather
   than retry.

   These checks are made by the owner's own clients, because only they
   can see scopes and limits. A receiver cannot verify them.

9.5.  Receiver-Side Authority

   A receiver checks each intent in a request or message from sender
   client S of principal P, with grants G presented alongside it:

   1.  Validate the intent (Sections 9.2 and 9.3).

   2.  If S is a device in P's view, or P is the receiver's own address,
       accept.

   3.  Let name be the intent name without its version. If name is
       handoff.human, info.request or info.answer, or starts with
       session., accept. None binds anyone to anything: a handoff only
       asks for a person, a live session is a channel the receiver may
       decline, and what may be disclosed is the answering side's
       decision (Section 9.3.2).

   4.  Look for a grant in G that is valid for (P, S, receiver, name)
       (Section 9.6.2). If one is found: if the intent's committed
       amount is greater than the grant's limits.commit_usd (0 if
       absent), reject with a limit error; otherwise accept.

   5.  If P's card names S as intake and the intake's intents cover name
       (exact match, or a pattern ending in * that is a prefix): if the
       intent's committed amount is greater than 0, reject with a limit
       error, because an intake agent cannot commit money; otherwise
       accept. An intake agent can therefore send pay.request.

Experimental           Signet Protocol, Version 0          November 2026

   6.  Otherwise reject: the agent has no grant to send this intent to
       this receiver.

   A client's own agents are trusted by its own clients without grants
   (step 2), because the owner already limits them with scopes.

9.6.  Grants

9.6.2.  Grant Validation

   A grant g is valid for principal P, agent S, receiver R and intent
   name at time now when all of these hold:

   1.  g.principal equals P;

   2.  g.agent equals S;

   3.  g.counterparty equals R, lowercased;

   4.  g.expires is after now;

   5.  g.id is not in the revokedGrants of P's contact view, as far as
       the receiver knows it;

Foss                    Expires 15 May 2027                    [Page 79]

Experimental           Signet Protocol, Version 0          November 2026

   6.  some entry of g.intents equals name, or ends in * and is a prefix
       of name without the *;

   7.  g.sig verifies with one of the grant keys of P's card (Section
       3.8).

   Rule 7 keeps grants valid across a rotation, because rotated-out keys
   are still grant keys. It voids grants signed before a recovery,
   because whoever holds the old key may not be the owner.

9.6.3.  Revoking a Grant

   The owner revokes a grant by appending a revoke-grant entry to its
   account log and publishing (Section 3.10). The id then appears in the
   contact view's revokedGrants. A receiver sees the revocation only
   through the contact view, so a receiver without the view cannot see
   revocations. Owners SHOULD release their view to every counterparty
   they grant to.

10.2.1.  Signed Delivery

      POST /v0/deliver        (domain-authenticated)

   4.6). It MUST refuse with 400 a delivery that carries a token, and
   with 403 a delivery whose from is absent or not on the authenticated
   domain. It then delivers locally.

10.2.2.  Local Delivery

   For each delivery:

   1.  Refuse with 400 an unknown kind, a token on a request, or a
       delivery with neither from nor token.

   2.  For each address in to: if it is not on this domain or not
       enrolled, list it as unknown. If the delivery has a token,
       compute the token hash for this address (Section 10.3); if it is
       registered, store the item in the mailbox with an empty from and
       sealed: true, otherwise park it (Section 10.3.3), or list the
       address as rejected if parking fails. Otherwise, for a request,
       count it against the per-sender and per-sender-domain limits for
       this recipient (Section 4.10) and list the address as rejected if
       either is exceeded. Otherwise store the item with from set to the
       sender.

10.3.  Delivery Tokens

10.3.1.  Tokens

   A thread's delivery token for an epoch is:

      token = b64u(MLS-Exporter("signet delivery v0", "", 32))

   using the MLS exporter of Section 8.5 of [RFC9420] with an empty
   context. Only members of the thread at that epoch can derive it.
   After a member is removed it cannot derive the next epoch's token.

   A reply token is 32 random bytes in b64u. A sender puts one in a
   request so the recipient can send its welcome sealed before any
   thread exists (Section 7.2).

   The token hash for a recipient address is:

      tokenHash = sha256(token || "|" || lowercase(address))

   computed over the UTF-8 string and written in sha256: form. Binding
   the hash to the address means one member's registration does not
   authorise deliveries to another.

10.3.2.  Registration

      POST /v0/delivery-tokens        (client-authenticated)
      { "add": ["sha256:…"], "remove": ["sha256:…"] }
      → { "ok": true, "released": 2 }

   Each client registers the token hash for its own address after
   creating or joining a thread, after each commit it makes or applies
   (for the new epoch), and before sending a request (for the reply
   token).

   A client SHOULD keep the hashes of the last 3 epochs of each thread
   registered, so that messages sent just before a commit still arrive,
   and SHOULD remove older ones. When it leaves a thread, it SHOULD
   remove all of that thread's hashes.

   released is the number of parked items moved into the mailbox by this
   registration.

10.3.3.  Parking

   A sealed delivery may arrive before the recipient has joined the
   thread and registered its token. The recipient's server holds such an
   item for at most 24 hours, with at most 500 parked items per address,
   counting only unexpired ones.

   When a hash is registered, every unexpired parked item with that hash
   is moved into the mailbox in arrival order. A client that registers a
   hash during a sync SHOULD fetch its mailbox again.

10.4.  Oblivious HTTP

10.4.1.  Gateway

   A home server MAY run an Oblivious HTTP gateway [RFC9458]. It
   publishes the gateway URL and key configuration in its policy
   (ohttp.gateway, ohttp.keys) and serves the key configuration at GET
   /.well-known/ohttp-gateway (Content-Type: application/ohttp-keys).

   The key configuration is one entry of the application/ohttp-keys
   format (Section 3 of [RFC9458]), with a 2-byte length prefix, and in
   the policy it is that byte string in b64u. Version 0 uses:

   *  KEM: DHKEM(X25519, HKDF-SHA256), 0x0020;

   *  KDF: HKDF-SHA256, 0x0001;

   *  AEAD: AES-128-GCM, 0x0001.

   Requests and responses are encapsulated as in Section 4 of [RFC9458],
   with media types message/ohttp-req and message/ohttp-res. The inner
   message is a known-length Binary HTTP message [RFC9292].

      POST /v0/ohttp        (Content-Type: message/ohttp-req)

Foss                    Expires 15 May 2027                    [Page 85]

Experimental           Signet Protocol, Version 0          November 2026

   The gateway:

   1.  refuses with 415 any other content type, and with 400 a request
       it cannot decapsulate (unknown key id or suite, or a failed
       open);

   2.  decodes the inner Binary HTTP request;

   3.  runs it only if it is POST /v0/deliver-sealed or POST
       /v0/deliver-anonymous; any other inner request gets an inner 403
       response;

   4.  returns the inner JSON response, encapsulated, with an outer 200.

   The gateway never runs a domain-authenticated or client-authenticated
   route.

10.4.2.  Relay

   An OHTTP relay is a separate service:

      POST /v0/relay?domain={domain}        (Content-Type:
        message/ohttp-req)

   The relay:

   1.  refuses with 404 any other route, with 415 any other content
       type, and with 400 a missing domain;

   2.  resolves domain's policy (Section 6) and refuses with 404 if it
       has no ohttp gateway, so the relay cannot be pointed at arbitrary
       URLs;

   3.  forwards the body to the policy's gateway URL with only the
       content type;

   4.  returns the gateway's body as message/ohttp-res, or 502 if the
       gateway did not answer with success.

   A relay MUST NOT log request contents or forward client-identifying
   headers. The relay learns which home server is sending and to which
   domain, but not the content. The gateway learns the content but sees
   only the relay's address. This holds only if relay and gateway do not
   collude.

10.4.3.  Use by Home Servers

   A home server configured with a relay sends every sealed and
   anonymous delivery to a domain that publishes an ohttp gateway
   through the relay, encapsulated with that domain's key configuration.
   The inner request is POST to the target route at the authority of the
   policy's server, with a JSON body. Otherwise it posts to the route
   directly. Signed deliveries never use the relay, because they name
   the sending domain anyway.

10.5.  Anonymous Requests

   A first-contact request can be sent with a Privacy Pass token
   [RFC9576] instead of a sender. The sender's home server acts as
   attester, a separate issuer signs blinded token requests, and the
   recipient's home server acts as origin.

10.5.1.  Token Type

   Version 0 uses publicly verifiable tokens, type 0x0002 [RFC9578], on
   RSA blind signatures, RSABSSA-SHA384-PSS-Deterministic [RFC9474],
   with a 2048-bit modulus and a 48-byte salt. The token challenge
   (Section 2.1 of [RFC9577]) is: token_type = 0x0002; issuer_name = the
   issuer's name; redemption_context = empty; origin_info = the
   recipient's domain.

   Tokens are bound to the recipient's domain, not to a session. A token
   is carried in b64u as anonymousToken.

10.5.2.  Obtaining a Token

   1.  The client reads the recipient domain's policy. It MUST have
       privacyPass. The reference client sends anonymously by default
       when it does.

   2.  The client fetches its own home server's issuer: GET /v0/issuer
       (client-authenticated) returns {"name", "publicKey"}, where
       publicKey is a DER SubjectPublicKeyInfo in b64u. The home server
       returns 501 if it has no issuer. If name is not the recipient's
       privacyPass.issuer, the client cannot send anonymously.

   3.  The client builds a token request with a random 32-byte nonce,
       blinds it, and sends POST /v0/tokens {"blinded": ["b64u"]}.

   4.  The home server (attester) refuses with 403 a client without
       send, counts each blinded message against the user's daily limit
       (429 when exceeded), and forwards POST /v0/issue {"blinded":
       [...]} to the issuer with domain authentication.

   5.  The issuer authenticates the domain (401 on failure), counts the
       blinded messages against the domain's daily limit (429 when
       exceeded; reference default 100000), and returns {"signatures":
       ["b64u"]}.

   6.  The client unblinds the signature and verifies the finished token
       before using it.

   The issuer never sees the token. The attester never sees the token
   either: it sees only the blinded message. The issuer also serves its
   public key at GET /v0/issuer-key.

10.5.3.  Redeeming a Token

   The sender's home server delivers the anonymous request locally or
   with POST /v0/deliver-anonymous (directly or through OHTTP):

      { "id": "i_…", "to": ["bob@example.net"], "kind": "request",
        "payload": { "to": "bob@example.net", "copies": [ "…" ] },
        "anonymousToken": "b64u" }

   The recipient's home server:

   1.  refuses with 400 a delivery that is not a request with an
       anonymousToken;

   2.  refuses with 403 if it accepts no issuer;

   3.  verifies the token: type 0x0002, a token_key_id matching a
       trusted issuer key, a challenge digest equal to SHA-256 of the
       challenge for its own domain, and a valid signature; refuses with
       403 otherwise;

   4.  records the token nonce as spent, and refuses with 403 if it was
       already spent;

   5.  for each address, lists it as unknown if not enrolled here, as
       rejected if the recipient has received more than the daily limit
       of anonymous requests (reference default 200), and otherwise
       stores the item with an empty from and sealed: true.

   An issuer MUST keep its signing key across restarts, and an origin
   MUST keep spent nonces across restarts at least until the issuer key
   changes. Otherwise tokens stop verifying, or one token can be spent
   twice.

   The recipient's server learns only that a rate-limited Signet user
   sent the request. The sender is named only inside the sealed copies,
   which the recipient's clients verify (Section 7.5).

10.6.  Relaying and Retries

   To relay a delivery to another domain, the home server resolves the
   domain's policy and posts a signed delivery to POST /v0/deliver with
   domain authentication, or a sealed or anonymous delivery to the
   matching route, through OHTTP when configured (Section 10.4.3).

   A response of 400 to 499, other than 429, is permanent. Any other
   failure, including a network error, an OHTTP relay failure and 429,
   is temporary.

   On a permanent failure, the home server bounces at once. On a
   temporary failure, it lists the addresses as queued and retries. The
   reference schedule waits 1 minute, 5 minutes, 30 minutes, 2 hours, 6
   hours, then 24 hours four times, about 4.4 days in all (10 attempts),
   before bouncing.

        "reason": "delivery to example.net failed: 404 …" } }

10.8.  Open Issues

   *  *Padding and batching.* MLS messages are padded to 256 bytes, but
      sealed requests, welcomes and the delivery envelope are not, and

      acknowledge mailbox items, so a server cannot know when every
      reading client has an item and it can be deleted. A future version
      should add one.

   *  *One relay, one issuer.* Version 0 assumes one relay and one
      issuer operator. Collusion between relay and gateway, or between
      issuer and origin, removes the corresponding protection.

11.  Humans-only Mail and Escrow

11.1.  Principle

   A sender can mark a request, a thread message or a plain email as
   humans-only, for example a password reset or a sign-in code, to ask
   that the recipient's agents not read it. *The sender only asks; the
   recipient decides.* The recipient's signed audience policy says which
   of its clients receive humans-only mail. By default these are its
   devices. The organisation's escrow client always receives it.

   Humans-only is enforced cryptographically: humans-only content is
   encrypted only to the clients the policy allows. It is not a control
   over the recipient. Nothing stops a recipient from showing a message
   to an agent, and Signet does not try to.

11.2.  Humans-only Requests

   A sender marks a request humans-only by setting audience to humans in
   the request body (Section 7.2) and sealing it to the card's humanKeys
   instead of requestKeys (Section 7.3). This applies even when the
   recipient has an exclusive intake: a humans-only request bypasses the
   intake unless the owner has opted the intake agent in.

   A recipient that accepts a humans-only request MUST start a
   humans-only thread (Section 11.4), not an ordinary one.

11.3.  Audience Policy

   A client reads humans-only mail if it is a device, if it is the
   org-escrow client, or if its client id is in the account's
   agentsReadHumansOnly set.

   The owner sets agentsReadHumansOnly with a set-audience-policy log
   entry (Section 3.5.1). Each entry replaces the whole set. Every id in
   it MUST be a client in the log.

   The policy is published in two places, both signed by the identity
   key:

   *  the card's humanKeys lists the agreement key of every active
      client that reads humans-only mail (Section 4.3);

   *  each member of the contact view has a humansOnly flag (Section
      4.4).

   Opting an agent in lets the owner overrule an over-cautious sender: a
   sender cannot keep the owner's own assistant out against the owner's
   wishes.


Foss                    Expires 15 May 2027                    [Page 90]

Experimental           Signet Protocol, Version 0          November 2026

11.4.  Humans-only Threads

   A message in a conversation cannot be encrypted to only some members
   of an MLS group. Humans-only messages therefore go to a separate MLS
   group of the same people, a humans-only thread, whose members are
   only the clients that read humans-only mail.

   1.  A client sending a humans-only message in an ordinary thread uses
       the humans-only thread linked to it. If there is none, it starts
       one (Section 8.5) with the other principals of the ordinary
       thread, with humansOnly set and linkedTo naming the ordinary
       thread, and records the link.

   2.  Every message sent in a humans-only thread carries audience:
       "humans".

   3.  A client MUST NOT start a humans-only thread unless it is itself
       a humansOnly member of its own view. An agent that is not opted
       in cannot open one.

   4.  The welcome carries humansOnly: true and linkedTo (Section 8.6).
       A joining client MUST reject the welcome if any member is not
       humansOnly in its owner's view.

   5.  A client MUST reject a commit to a humans-only thread that adds a
       member who is not humansOnly (Section 8.8).

   6.  A rekey of a humans-only thread removes members who are no longer
       humansOnly and adds members who now are (Section 8.8).

   Clients SHOULD show the two linked threads together.

11.5.  Escrow

   An organisation can enroll one or more org-escrow clients for an
   account, for example for legal hold or compliance archiving. Escrow
   that skips some mail is not escrow, so neither the sender's flag nor
   the owner's audience policy can keep it out.

   1.  An org-escrow certificate MUST have scopes covering read:*. A log
       that adds one without it MUST be rejected (Section 3.7).

   2.  Every active escrow client is added to the card's requestKeys,
       even when the intake is exclusive (Section 4.3).

   3.  Every active escrow client reads humans-only mail, so it is in
       humanKeys and is humansOnly in the view.

   4.  In the contact view an escrow client has kind escrow and reads:
       true, so it joins every thread, including humans-only threads.

   5.  An escrow client receives a copy of every legacy email (Section
       11.6).


Foss                    Expires 15 May 2027                    [Page 91]

Experimental           Signet Protocol, Version 0          November 2026

   Contacts who have the view are told plainly that escrow receives
   everything, by its escrow kind. A client SHOULD show this to its user
   when an escrow client is present in a thread.

11.6.  Humans-only Plain Email

   Plain email is marked humans-only with this header field:

      Signet-Audience: humans

   A message is humans-only if its header block, after unfolding,
   contains a Signet-Audience field (case-insensitive name) whose value
   is humans after trimming whitespace.

   A Signet home server that receives plain email for an enrolled
   address (Section 13.3) seals it to every active client whose scopes
   cover read:* and every active escrow client; if the message is
   humans-only, only to those of them that read humans-only mail
   (Section 11.3).

   A client that sends plain email for a humans-only purpose SHOULD add
   the header. The reference home server adds it when the client asks
   (Section 13.2).

   In Gmail mode (Section 13.6) nothing can be sealed, because the
   provider holds the plaintext. A client scanning Gmail MUST apply the
   policy itself: it MUST skip humans-only messages unless it is a
   humansOnly member of its own view (or, if it is not in the view,
   unless it is a device).

11.7.  Open Issues

   *  *The header is unauthenticated.* Signet-Audience is not covered by
      the Signet attestation (Section 13.2) and is usually outside DKIM
      signatures, so any hop can add or remove it. Removing it exposes a
      humans-only email to agents; adding it hides an ordinary email
      from them.

   *  *Gmail mode relies on the client.* In Gmail mode the policy is
      applied by each client, not by encryption. A client that ignores
      it can read humans-only mail.

   *  *Escrow is not visible on the card.* Request keys are unlabeled,
      so a stranger sending a first request cannot tell that an escrow
      client will receive it. Only contacts with the view see the escrow
      kind. A future version may flag escrow keys on the card.

12.  Live Sessions and Handoff

12.1.  Overview

   Thread messages are durable and asynchronous. When two agents need
   fast back-and-forth, for example to settle a meeting time through
   several rounds, a thread can move to a live session using the

Foss                    Expires 15 May 2027                    [Page 92]

Experimental           Signet Protocol, Version 0          November 2026

   Agent2Agent (A2A) protocol, version 0.3 [A2A], which is JSON-RPC 2.0
   over HTTP.

   A live session is a side channel of its thread:

   *  The offer travels inside the thread, so only members see the
      endpoint.

   *  The bearer token is derived from the thread's MLS exporter, so it
      is never sent and only current members can compute it.

   *  Nothing binding happens in a live session. Commitments come back
      to the thread as signed messages and intents, where scopes and
      grants apply (Section 9).

   handoff.human is the opposite move: it takes a thread away from
   agents and gives it to the owner.

12.2.  Offering a Session

   An agent that runs an A2A endpoint (the host) offers a session by
   sending a thread message with a session.offer intent:

      {
        "name": "session.offer",
        "args": {
          "protocol": "a2a",
          "url": "https://agent.example.com",
          "sessionId": "s_Vb2m0aL2vTq1xYb0aLcd",
          "expires": "2026-11-11T10:00:00.000Z",
          "cardHash": "sha256:…"
        }
      }

   +===========+========+==========+===================================+
   | Arg       | Type   | Required | Meaning                           |
   +===========+========+==========+===================================+
   | protocol  | string | yes      | MUST be a2a.                      |
   +-----------+--------+----------+-----------------------------------+
   | url       | string | yes      | The host's A2A base URL.          |
   +-----------+--------+----------+-----------------------------------+
   | sessionId | string | yes      | s_ followed by 12 random bytes in |
   |           |        |          | b64u.                             |
   +-----------+--------+----------+-----------------------------------+
   | expires   | string | yes      | When the offer and session end.   |
   |           |        |          | The reference default is 30       |
   |           |        |          | minutes after the offer.          |
   +-----------+--------+----------+-----------------------------------+
   | cardHash  | string | no       | H(agentCard) of the host's A2A    |
   |           |        |          | agent card (Section 12.4).        |
   +-----------+--------+----------+-----------------------------------+

   Sending the offer needs the intent:session.offer scope like any other
   intent (Section 9.4). Receivers accept session.* intents from any

Foss                    Expires 15 May 2027                    [Page 93]

Experimental           Signet Protocol, Version 0          November 2026

   agent in the thread without a grant (Section 9.5), because a session
   is a channel the receiver may decline.

   The host records the session: its thread, its role (host), the URL,
   the card hash and the expiry.

12.3.  Session Token

   Both sides derive the bearer token from the thread's current epoch:

      liveToken = b64u(MLS-Exporter("signet live v0 " || sessionId, "",
        32))

   Only members of the thread at the current epoch can derive it. A
   commit changes the epoch and so the token: after a rekey (for
   example, after an agent is revoked), sessions using the old token
   stop working, and a member that is still in the thread can join again
   with the new token.

12.4.  Host Gateway

   The host serves GET /.well-known/agent-card.json and POST / (JSON-RPC
   2.0).

   The agent card follows A2A 0.3, with protocolVersion 0.3.0 and this
   security scheme:

      {
        "securitySchemes": { "signet": { "type": "http",
          "scheme": "bearer",
          "description":
          "Token derived from the Signet thread (MLS exporter)" } },
        "security": [ { "signet": [] } ]
      }

   For POST /, the gateway reads at most 1,000,000 bytes and then:

   1.  Takes the bearer token from the Authorization header and the
       session id from params.message.metadata.sessionId.

   2.  Authorises the call. It succeeds only if the session exists with
       role host, has not expired, its thread is still one the host is a
       member of, the thread has no pending handoff (Section 12.6), and
       the token equals the current liveToken in a constant-time
       comparison. On failure it answers HTTP 401 with JSON-RPC error
       -32001 ("not a current member of this session").

   3.  Accepts only the method message/send. Any other method gets
       JSON-RPC error -32601.

   4.  Passes the concatenated text parts of the message to the agent
       and returns a result of kind message, role agent, with the answer
       as one text part and metadata.sessionId set.


Foss                    Expires 15 May 2027                    [Page 94]

Experimental           Signet Protocol, Version 0          November 2026

   5.  Reports any other failure as JSON-RPC error -32603.

   Other paths return 404.

12.5.  Joining and Ending

   A member (the guest) that receives a thread message with a
   session.offer intent MAY join:

   1.  Require the message to be in this thread, the offer not expired,
       and (for an agent) no pending handoff by its own account.

   2.  Fetch {url}/.well-known/agent-card.json. If the offer has a
       cardHash, the card's hash MUST equal it; otherwise do not join. A
       guest MUST NOT join a url that is not HTTPS, except in local
       testing.

   3.  Record the session with role guest.

   4.  Send message/send calls with Authorization: Bearer {liveToken}
       and metadata.sessionId.

   The host ends a session by sending a thread message with a
   session.end intent naming the session id and an optional reason.
   Every member that receives it forgets the session. A session also
   ends when it expires, when the epoch changes (Section 12.3), and on a
   handoff (Section 12.6).

12.6.  Handoff to a Human

   handoff.human marks a thread as needing its sender's owner. Its
   reason says why. Any client may send it; agents need no scope for it.

   When a client sends handoff.human, it records that the thread is
   handed to its own address, with the reason and the time, and forgets
   every live session on the thread.

   When a client receives a message with handoff.human, it records that
   the thread is handed to the sender's address and forgets every live
   session on the thread. If the sender is the client's own address, it
   reports a handoff event, so the owner's devices can show the thread
   as needing them.

   While a thread is handed to an account:

   *  that account's agents and tools MUST NOT send in the thread,
      except another handoff.human, and MUST NOT join live sessions in
      it;

   *  the host gateway refuses all session calls for the thread (Section
      12.4, step 2);

   *  the other side's agents are not held.


Foss                    Expires 15 May 2027                    [Page 95]

Experimental           Signet Protocol, Version 0          November 2026

   The handoff ends when one of the account's devices sends a message in
   the thread that is not itself a handoff. Every client that receives
   such a message from a device of the account the thread was handed to
   clears the handoff.

12.7.  Open Issues

   *  *Holds are enforced by the owner's own clients.* Receivers do not
      reject an agent's message in a thread its account handed off. An
      agent that ignores the hold can still send.

   *  *Exposure of the endpoint.* The offer reveals the host's endpoint
      to every thread member, and the guest connects to it directly, so
      the host learns the guest's network address.

   *  *No hosted gateway.* An agent without its own HTTP endpoint cannot
      host a session. A hosted A2A gateway is future work.

   *  *One method.* Version 0 live sessions use only message/send, with
      text parts. Streaming, tasks and file parts of A2A are not
      supported.

13.  Interoperability with Email

13.1.  Overview

   Signet keeps working with plain email [RFC5322] in both directions:

   *  *Signet to email.* A Signet user can send plain email to anyone.
      It carries a Signet header field, attested by the sender's domain,
      so a Signet-aware recipient can check it and move the conversation
      to Signet.

   *  *Email to Signet.* A Signet home server can receive plain email
      for its users. It checks SPF, DKIM and DMARC, encrypts the message
      to the recipient's reading clients on arrival, and keeps no
      plaintext.

   *  *Alongside an existing provider.* A domain can keep its existing
      mail provider. Its users send plain email through that provider
      (Gmail mode, Section 13.6) and receive plain email there.

13.2.  Outbound Plain Email

13.3.  Inbound Plain Email

   A home server MAY accept plain email over SMTP [RFC5321] for its
   domain. If it does:

   1.  It MUST refuse with 550 any recipient that is not an enrolled
       address on its domain.

   2.  It SHOULD offer STARTTLS. The reference server offers it when
       configured with a certificate, and does not offer AUTH.

   3.  It MUST evaluate SPF [RFC7208], DKIM [RFC6376] and DMARC
       [RFC7489] on the message and record each result as a string
       (pass, fail, none, and so on). DKIM is pass if any signature
       passes.

   4.  For each recipient, it MUST seal the raw message, as received, to
       that recipient's legacy readers (Section 11.6) with HPKE (the
       suite of Section 7.3), info = signet0 legacy  followed by the
       recipient's address.

   5.  It stores the sealed mail in the recipient's mailbox with kind
       legacy and from set to the envelope sender, and MUST NOT keep the
       plaintext.

   6.  If sealing or storing fails, it answers 451.

   The reference server limits messages to 40 MiB.

      {

13.4.  Reading Plain Email

   A client that finds a legacy item:

   1.  Ignores it if there is no copy for its client id: the recipient's
       policy kept this client out.

   2.  Opens its copy and parses the message.

   3.  Takes the sender from the first From address, or the envelope
       sender if there is none.

   4.  Checks any Signet header field (Section 13.5).

   5.  Checks the sender's domain for lookalikes (Section 7.8).

   6.  Puts the message in the inbox tier only if DMARC passed, the
       sender is trusted (Section 7.7), and the domain is not a
       lookalike. Otherwise it puts it in the request tier.

   7.  Notes whether it is humans-only.

   Plain email was readable in transit. Clients MUST show it at a lower
   trust level than Signet mail, whatever its tier.

13.5.  Checking a Signet Header

   A recipient checks a Signet header field on plain email with From F,
   To list T and Subject S:

   1.  Parse the value: remove all whitespace, split on ;, and read
       key=value pairs. If v is not signet0 or server or fp is missing,
       ignore the header.

   2.  Let A be addr if present, otherwise F, normalized.

   3.  Look up A (Section 5.8). If the lookup fails, the result is not
       on Signet and not authenticated.

   4.  onSignet is true if A is enrolled and sha256 of its identity key
       equals fp.

   5.  authenticated is true if onSignet is true, F's domain has a
       Signet policy, and the attestation verifies with that domain's
       key over F, T, S and the header's fp, addr, ts and nonce, with ts
       no more than 5 minutes in the future and no more than 7 days in
       the past.

   The attestation MUST come from F's own domain: nobody else can vouch
   for mail from that address.

   Clients MUST report onSignet and authenticated separately. onSignet
   says only that the address is enrolled with that key; anyone can
   paste a fingerprint. Only authenticated says something about this
   message. SPF, DKIM and DMARC still decide the message's tier (Section
   13.4). A client MAY offer to continue an authenticated conversation
   over Signet.

13.6.  Gmail Mode

   A domain that keeps Google Workspace, or a user on consumer Gmail,
   can use Signet alongside it:

   *  *Sending.* The client gets an attested header from its home server
      (POST /v0/legacy/attest) and sends the message through the Gmail
      API with the Signet field and, if humans-only, Signet-Audience:
      humans.

   *  *Scanning.* The client lists messages added since a stored history
      id, reads the From, To, Subject, Message-ID, Signet and
      Signet-Audience header fields, and checks each Signet field
      (Section 13.5). It applies the humans-only policy itself (Section
      11.6).

   Sending needs the gmail.send scope. Scanning headers needs
   gmail.metadata, a restricted scope that needs Google verification for
   public apps.

13.7.  Choosing Between Signet and Email

   When a user writes to an address, the reference client:

   1.  Looks the address up. If the domain does not support Signet or
       the address is not enrolled, sends plain email.

   2.  If there is a thread whose only participants are the user and
       that address, sends in it.

   3.  Otherwise sends a request, with the first 500 characters of the
       text as the note.

13.8.  Outbound Transport

   A home server sends plain email through a configured relay or
   directly to the lowest-preference MX of each recipient domain,
   optionally DKIM-signing it with the domain's key. When sending
   directly, a conforming home server MUST apply the recipient domain's
   MTA-STS policy [RFC8461] and SHOULD use DANE [RFC7672] where
   available.

13.9.  Open Issues

   *  *Header replay.* The attestation covers From, To and Subject and
      is valid for 7 days. Recipients do not track nonces, so the same
      header can be replayed on another message with the same From, To
      and Subject within that time. The body is not covered.

   *  *Upgrading conversations.* Version 0 detects Signet senders in
      plain email but does not specify how a reply moves the
      conversation to Signet beyond sending a request.

14.  Security Considerations

14.1.  Threat Model

   Signet assumes that:

   *  the network is controlled by an attacker, except where HTTPS
      protects it;

   *  any home server may be curious, and some may be malicious;

   *  senders may be malicious, including other users' agents;

   *  a client may be lost or compromised;




Foss                   Expires 15 May 2027                    [Page 101]

Experimental           Signet Protocol, Version 0          November 2026

   *  the transparency log operator follows the protocol, and its
      misbehaviour can be detected but not prevented by a single client
      (Section 14.6).

14.2.  What a Home Server Can and Cannot Do

   A home server cannot:

   *  add a client to an account, change a card or view, or forge a
      grant, because these are signed by the identity key and checked on
      every lookup;

   *  read requests, thread messages, attachments or legacy mail after
      arrival, because these are sealed to clients;

   *  send as one of its users in a way other Signet users accept,
      because requests and messages are signed by client keys from the
      sender's view.

   A home server can:

   *  refuse service, drop deliveries, delay them or serve errors;

   *  withhold a contact view, or release it to a requester the owner
      did not choose (Section 4.11);

   *  see metadata (Section 15);

   *  rebind an address to a new identity key it controls.

   A rebinding must be appended to the transparency log, or
   correspondents who check the log refuse the entry (Section 5.8). Once
   logged, correspondents who pinned the old key refuse the new one
   (Section 3.8), and the owner's monitoring reports it (Section 5.9). A
   rebinding is therefore not silent. It can still succeed against
   correspondents who look the address up for the first time.

14.3.  Trust on First Use

   A client pins an identity key the first time it verifies an address.
   A domain that rebinds an address before a correspondent's first
   lookup is not detected by that correspondent. The owner's monitoring
   detects it. Clients SHOULD let users compare identity-key
   fingerprints out of band for high-value contacts.

14.4.  Identity Key Loss and Compromise

   Rotation (Section 3.6) replaces an identity key the owner still
   holds. It is for routine hygiene and for when a device that held the
   key is lost but the key is not believed copied. Contacts follow the
   chain silently.

   Recovery (Section 3.9) replaces an identity key the owner no longer
   holds. It is visible to contacts as recovered, and it voids grants

Foss                   Expires 15 May 2027                    [Page 102]

Experimental           Signet Protocol, Version 0          November 2026

   signed before it. Clients SHOULD tell their users when a contact's
   key was recovered, because the old key may be in someone else's
   hands.

   A recovery key does not protect against theft of the identity key.
   Whoever holds the identity key can rotate it, add clients, sign
   grants and name a new recovery key. If the thief replaces the
   recovery key, the owner cannot recover. The only remedy is a
   rebinding by the domain, which contacts will see as an identity
   change. Owners SHOULD keep the identity key on as few devices as
   possible and the recovery key offline.

   Anyone who obtains the recovery key while the identity key is still
   in use can take the account over with a recover entry. Contacts see
   this as a recovery. The owner's own clients, whose certificates
   survive the recovery, report a key-changed event with how equal to
   recovered for their own address (Section 3.8), but the history check
   of Section 5.9 does not alert, because the new key is on the chain.
   Clients MUST show the owner a recovery of its own address that it did
   not start. Owners MUST protect the recovery key at least as well as
   the identity key.

   After a recovery, existing clients remain certified. The owner SHOULD
   revoke any client it did not enroll, then rekey its threads.

14.5.  Client Compromise and Revocation

   A compromised client can do whatever its scopes allow until it is
   revoked. Revocation takes effect at once for home-server access
   (Section 3.11), new requests and new threads; in an existing thread,
   only after a member rekeys it (Section 8.8). Until then the revoked
   client remains an MLS member and can read new messages.

   Clients SHOULD rekey every thread an account shares as soon as they
   see a client of a participant revoked or expired. Certificates expire
   (Section 3.4.1), which bounds how long a forgotten client stays
   usable.

14.6.  Transparency Log

   The log gives detection, not prevention:

   *  A log that shows different trees to different clients (a split
      view) is caught only when two views meet: a client's stored tree
      head against a later one (Section 5.8.1), or two parties comparing
      heads. Version 0 has no gossip, so a targeted split view against a
      client that never talks to anyone else is not caught.

   *  A log can withhold a newer leaf and serve an older one as
      "latest". The owner's monitoring of its own history is what
      catches a withheld rebinding.

   Deployments SHOULD use at least two independent log operators and
   SHOULD have clients or monitors exchange tree heads.

Experimental           Signet Protocol, Version 0          November 2026

14.7.  Signatures and Canonicalization

   All signatures are over canonical JSON (Section 3.2). Implementations
   MUST use the same canonical form for signing and verifying, and MUST
   reject non-I-JSON input. Two implementations that disagree on
   canonical form will reject each other's signatures. They will not
   accept a forgery.

   The identity key signs several kinds of object: log entries, key
   links, cards, views and grants. Cards, views and grants have a type
   member, key links have distinct type values, and log entries have a
   different shape (seq, prev, ts, body). The domain key signs bindings,
   not-enrolled answers, domain-authenticated requests and legacy
   attestations, each with a distinct type, kind or status. These
   distinctions keep a signature on one kind of object from being valid
   on another. A future version should add an explicit context string to
   every signed object.

14.8.  Replay

   *  Client and domain authentication accept any request within 5
      minutes of the server's clock and do not track repeats (Section
      3.12).

   *  A recovery proof is valid for 5 minutes and is not single-use
      (Section 3.12).

   *  A plain-email attestation is valid for 7 days and its nonce is not
      tracked (Section 13.9).

   *  Requests carry an id and ts but recipients do not reject
      duplicates. The per-sender daily limit bounds how many a replaying
      server can deliver.

   *  Thread messages are protected against replay by MLS.

   *  Privacy Pass tokens are single-use at the origin (Section 10.5.3).

14.9.  Agents and Authority

   Scopes and commit_usd limits in certificates are enforced only by the
   owner's own clients. A compromised or modified agent can ignore them
   when sending. Receivers are protected by grants instead: an agent
   that is not the sender's intake for an intent, and has no grant
   naming the receiver, is refused, and an amount over the grant's limit
   is refused (Section 9.5).

   Requests and messages from strangers are untrusted input. An agent
   that reads them, especially an intake agent, MUST NOT treat
   instructions in their text or arguments as authority to act beyond
   its own scopes, and SHOULD hand off to its owner (Section 12.6) when
   asked to do something it is not sure it may do.



Foss                   Expires 15 May 2027                    [Page 104]

Experimental           Signet Protocol, Version 0          November 2026

   pay.request and pay.sent never move money (Section 9.3.1). A
   pay.request link is a classic phishing vector. A pay.sent is a claim,
   not a receipt from a payment system.

   Live sessions carry nothing binding. A receiver MUST NOT treat
   anything said in a live session as a commitment until it arrives as a
   signed intent in the thread.

14.10.  Spoofing

   Signet traffic cannot be spoofed without a client key from the
   sender's view: every request and message is signed by such a key, the
   view is signed by the identity key, the domain binds the identity
   key, and the log records the binding.

   Plain email remains plain email. A Signet header field is a hint
   unless its attestation verifies (Section 13.5), and SPF, DKIM and
   DMARC still decide plain email's trust.

   Lookalike domains are the remaining trick. Signet stops anyone
   sending as a domain, not registering a similar one. The lookalike
   check (Section 7.8) is a heuristic and will miss some confusables.

14.11.  Denial of Service

   *  Lookups, claims, requests and tokens are rate-limited per day
      (Section 4.10). Limits held in memory reset when the server
      restarts.

   *  An attacker can send up to 500 sealed deliveries with random
      tokens to fill a recipient's parking space (Section 10.3.3).
      Legitimate early deliveries are then rejected for up to 24 hours.
      Because a rejection is reported in the delivery result rather than
      as an HTTP error, the sending server does not retry.

   *  An attacker can claim a client's one-time key packages up to the
      per-requester and per-domain limits. The last-resort package keeps
      the client reachable, at the cost of reusing its init key.

14.12.  Implementation Status

   The MLS and VRF code in signet-mls (about 750 lines of Rust on top of
   OpenMLS and curve25519-dalek) and the rest of the reference code have
   not been audited. The VRF is checked against the [RFC9381] test
   vectors. Implementers SHOULD NOT rely on the reference code for
   protection of real data until it has been reviewed.

15.2.  Directory Enumeration

   Directory answers for unknown and unenrolled addresses are identical
   and signed (Section 4.5). Log leaves are filed under VRF outputs, so
   the log cannot be used to test guessed addresses offline (Section
   5.2). Lookups are rate-limited per requester, per domain and per IP,
   misses cost ten times as much as hits, and domains whose lookups
   mostly miss are cut off for the day (Section 4.7). These measures
   slow enumeration. They do not stop a patient attacker with many
   domains or IP addresses.

15.3.  What the Card Reveals

   The public card lists one request key per admitting client and one
   human key per client that reads humans-only mail. A stranger can
   therefore count an account's devices (plus opted-in agents and
   escrow) from humanKeys, and can see when that number changes. The
   card also publishes the key chain, including the public recovery key.

15.4.  Requester Hashes

   Requester hashes are unkeyed hashes of addresses (Section 4.7).
   Anyone who can guess an address can compute its hash. Remote servers
   and the log can link a user's lookups across time and, by guessing,
   identify the user.

15.5.  Metadata That Still Shows

   *  Servers see the thread id of every thread message, commit and
      welcome, so they can link all traffic of a thread (Section 8.11).
      Delivery tokens additionally link deliveries within an epoch.

   *  Timing and sizes are visible. MLS messages are padded to 256
      bytes; requests, welcomes and envelopes are not, and nothing is
      batched.

   *  A request sent with anonymous: false, or to a domain without
      Privacy Pass, names the sender on the envelope.

   *  A welcome sent to someone who did not send a request (a thread
      started directly, not by accepting) carries the sender on the
      envelope, because there is no reply token to seal it with.

   *  OHTTP protects the sending server's identity only if relay and
      gateway do not collude. Privacy Pass protects the sender only if
      issuer and recipient's server do not collude.

   *  Plain email is readable by every hop before it reaches a Signet
      server, and by the provider in Gmail mode.

   *  A live session exposes each side's network address to the other
      (Section 12.7).

15.6.  Contacts and Labels

   Admission is decided on the recipient's clients, but the home server
   stores contacts and trusted domains in the clear so that all of an
   account's clients share them (Section 7.9). Client labels never
   appear in the directory. A label reaches a thread only if a client
   chooses to share it (Section 8.4).

15.7.  Escrow

   An escrow client receives everything, including humans-only mail.
   Contacts with the view see it as escrow. Strangers sending a first
   request do not (Section 11.7). Organisations that use escrow SHOULD
   say so to their correspondents.

15.8.  Retention

   A server SHOULD delete mailbox items once every reading client has
   them, expire blobs and parked items, and keep rate-limit counters no
   longer than their window.
